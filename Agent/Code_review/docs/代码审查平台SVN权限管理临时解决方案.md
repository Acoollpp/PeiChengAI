# 代码审查平台 SVN 权限管理临时解决方案

## 一、背景说明

当前代码审查平台采用 Web 服务模式运行，用户在页面提交 SVN 仓库地址和版本号后，由服务端统一拉取代码差异并触发审查任务。

该模式上线快、维护集中，但也带来一个阶段性问题：SVN 访问动作集中在服务端执行，用户原有 SVN 权限无法天然约束平台中的仓库访问。若只依赖用户手工填写地址，存在误提交或越权提交其他产品仓库地址的风险。

从长期架构看，后续计划参考 Cherry Studio 一类客户端架构，将部分能力下沉到客户端，让 SVN 访问尽量发生在用户本机或客户端侧，由 SVN 原生权限进行控制。但该方向涉及客户端框架、部署方式、升级机制和本地环境适配，短期内改造成本较高。

因此，本方案定位为临时解决方案：在现有 Web 平台上增加用户、管理员和 SVN 仓库授权能力，先把权限边界收敛到平台层，降低当前使用风险，并为后续客户端化重构沉淀基础数据。

## 二、方案目标

本次临时方案目标包括：

- 建立平台侧 SVN 仓库权限管理能力。
- 使用手机号作为临时唯一身份标识，延续当前登录方式。
- 增加管理员权限和管理员后台。
- 管理员可新增账号、管理账号状态、配置产品仓库权限。
- 普通用户仍可直接粘贴完整 SVN URL，减少使用习惯变化。
- 系统后端根据 SVN URL 自动识别仓库分类，并校验用户是否有权限。
- 管理员仪表盘展示平台使用情况，重点展示各用户任务使用次数。

## 三、实施范围

本方案包含四部分：

1. 用户与管理员体系

   在现有登录基础上增加管理员标识和账号启用状态。首批管理员通过环境变量配置，避免系统初始状态下无人可管理。

2. SVN 仓库权限体系

   按当前仓库分类建立权限规则。公共仓库默认开放，产品仓库按用户授权开放。

3. 管理员后台页面

   在平台右上角用户区域增加“管理后台”入口。管理员进入后可查看仪表盘、维护账号和管理仓库权限。

4. 仪表盘统计

   增加平台使用情况统计，必须包含“用户-任务数”图表，用于观察产品实际使用情况。

## 四、SVN 仓库权限划分

本次权限按照当前 SVN 仓库分类实施。

公共仓库默认所有登录用户可访问：

| 仓库 | SVN 地址 |
| --- | --- |
| 公共仓库 | `https://192.168.0.233/svn/02_public_repository` |
| 文档仓库 | `https://192.168.0.233/svn/documents` |

产品仓库由管理员按用户授权：

| 产品 | SVN 地址 |
| --- | --- |
| 高压 | `https://192.168.0.233/svn/src_energy` |
| 户储 | `https://192.168.0.233/svn/src_home` |
| 基站 | `https://192.168.0.233/svn/src_bs` |
| 动力 | `https://192.168.0.233/svn/src_moto` |
| 显示屏 | `https://192.168.0.233/svn/src_lcd` |
| Linux | `https://192.168.0.233/svn/src_linux` |
| 上位机 | `https://192.168.0.233/svn/src_PaceTools` |
| 电源 | `https://192.168.0.233/svn/src_power` |

## 五、用户使用方式

考虑到多数用户习惯从 SVN 工具、文档或工作群中直接复制完整仓库地址，本方案不强制拆分为“仓库选择 + 路径填写”。

用户仍在任务提交区粘贴完整 SVN URL，例如：

```text
https://192.168.0.233/svn/src_home/PCB_1447V320/SST22-1404-T
```

页面会额外展示“可用仓库”辅助区，列出当前用户有权限访问的仓库前缀。用户可点击仓库前缀快速填入，也可以直接粘贴完整地址。

最终权限判断由后端完成：

- 地址不属于已配置仓库时，系统拒绝提交。
- 地址属于公共仓库时，登录用户均可提交。
- 地址属于产品仓库时，只有被管理员授权的用户可以提交。
- 未授权提交会被拒绝，避免通过手动修改 URL 绕过页面限制。

## 六、管理员后台能力

管理员入口放在页面右上角，与当前用户名、手机号和退出按钮相邻。普通用户不展示入口，也不能直接访问后台地址。

管理员后台包含三类能力：

1. 仪表盘

   展示用户总数、管理员数量、任务总数、今日任务数、各状态任务数、仓库使用分布、最近任务列表，以及用户任务数图表。

2. 账号管理

   管理员可新增账号，维护姓名、手机号、是否管理员、是否启用等信息。

3. 仓库权限管理

   管理员可为每个用户勾选可访问的产品仓库。公共仓库默认开放，不需要单独配置。

## 七、仪表盘统计价值

本方案重点增加“用户-使用次数”图表，以任务数作为平台使用次数指标。

该图表可用于：

- 判断平台是否被实际使用。
- 识别核心使用用户和高频团队。
- 观察推广后使用量变化。
- 评估后续投入客户端化重构的优先级和收益。
- 发现异常使用或集中失败情况。

第一版图表建议使用横向柱状图，展示用户姓名、手机号和任务数。实现上不引入复杂前端依赖，降低交付风险。

## 八、预期收益

本方案落地后，可获得以下收益：

- 降低用户误提交或越权提交其他仓库的风险。
- 管理员可集中维护账号和仓库权限，不再依赖代码配置或人工沟通。
- 保留用户直接粘贴完整 SVN URL 的使用习惯，减少培训成本。
- 通过仪表盘掌握平台使用情况，为后续推广和资源投入提供依据。
- 为未来客户端化重构沉淀用户、仓库、授权和使用统计数据。

## 九、风险与控制措施

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 手机号身份不等同于强认证 | 可能存在他人冒用手机号登录 | 本阶段定位为临时治理；后续可接入企业统一身份 |
| 平台权限不是 SVN 原生权限 | 仍依赖平台后端校验 | 后端强制校验，不信任前端展示；长期通过客户端化解决 |
| 仓库清单变化 | 新仓库无法自动纳入权限 | 第一版内置清单，后续可改为配置文件或数据库维护 |
| 管理员误配置权限 | 用户可能无法提交或获得过宽权限 | 后台页面清晰展示公共仓库和产品仓库，后续可增加审计日志 |
| 仪表盘统计口径单一 | 任务数不能完全代表使用质量 | 第一版先用任务数衡量使用频率，后续可增加成功率、耗时、失败原因 |

## 十、实施计划

建议分三步实施：

第一步：权限基础能力

- 增加管理员字段和账号启用字段。
- 增加用户仓库权限表。
- 增加仓库清单和 SVN URL 识别逻辑。
- 在任务提交接口增加权限校验。

第二步：页面与管理能力

- 任务台增加可用仓库辅助展示。
- 右上角增加管理员入口。
- 新增管理员后台页面。
- 支持账号新增、账号编辑和仓库权限配置。

第三步：仪表盘与验证

- 增加仪表盘统计接口。
- 增加用户任务数图表。
- 增加仓库使用分布和最近任务列表。
- 补充自动化测试和手工验证。

## 十一、后续规划

本方案是 Web 架构下的 SVN 权限管理临时解决方案。后续建议继续推进客户端化方向：

- 将 SVN 访问逐步下沉到客户端侧。
- 使用用户本机 SVN 凭据和原生权限作为最终访问边界。
- 平台侧保留任务记录、报告展示、统计分析和管理能力。
- 已建设的用户、仓库、权限和统计数据可继续复用。

通过本方案，可以在不大幅调整现有架构的前提下，先解决当前 SVN 权限风险，并为后续架构升级建立可复用的数据基础和管理入口。
