# 【通用】代码变更审查维护说明

## 1. 说明目的

本文档用于指导 `通用-代码变更审查` skill 的后续维护工作。

重点说明：

- skill 执行代码审查时的整体流程。
- 当前规则分为输入、规则、输出三大模块的原因。
- 后续工程师上传规则文档后，Codex 如何自动识别、归类并更新规则文件。

## 2. Skill 总体流程

主入口文件：

```text
D:\skills\通用-代码变更审查\SKILL.md
```

具体规则文件：

```text
D:\skills\通用-代码变更审查\references
```

执行流程：

1. 输入模块收集项目路径、旧版本、新版本、输出路径。
2. 输入模块获取 SVN 差异材料。
3. 规则模块按产品、AI、架构执行审查。
4. 输出模块生成旧版七章结构报告。
5. 输出模块反馈报告路径和版本信息。

## 3. 三大模块

| 模块 | 职责 |
|---|---|
| 输入模块 | 准备审查材料，包括参数收集、SVN 差异获取和异常兜底 |
| 规则模块 | 执行风险判定，包括产品、AI、架构三类规则 |
| 输出模块 | 生成报告并反馈输出路径 |

## 4. 后续新规则添加方式

工程师优先上传规则文档，不需要手动判断目录。

Codex 必须：

1. 提取文档中的文本、表格、标题和规则条目。
2. 拆分为独立规则。
3. 判断属于输入、规则还是输出。
4. 如果属于规则模块，再判断属于产品、AI 还是架构。
5. 优先追加到已有子规则文件。
6. 无法承载时新增编号子规则文件。
7. 新增文件后更新对应 `README.md`。
8. 反馈来源文档、归类结果和修改文件。

## 5. 报告格式

代码审查报告固定使用旧版七章结构：

```text
# 代码变更审查报告

## 一、提交历史
## 二、变更文件清单
## 三、主要功能变更分析
## 四、Bug 修复验证
## 五、代码质量问题
## 六、风险评估
## 七、结论
```

## 6. 维护原则

- 不在 `SKILL.md` 堆叠具体规则。
- 具体规则放入 `references/` 下对应模块。
- 新增子规则文件必须更新对应 `README.md`。
- 强规则必须写清适用场景、判定依据、审查方法和输出要求。
