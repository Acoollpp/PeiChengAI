# 平台开发与任务管理复现指南

## 1. 文档目的

本文用于指导后续开发人员在现有代码审查平台中复现新的任务平台开发流程，明确从需求拆解、后端建模、前端页面、任务管理入口、权限控制到测试验证的完整路径。

后续新增平台功能时，优先沿用本文中的架构、权限、页面和验证方式，避免重复建设新的账号体系、存储体系或任务执行模型。文中同时保留了本次 GPIO 配置表、BOM 规格书匹配、白盒测试接入统一任务管理时形成的关键改动和验证结果，便于对照复现。

## 3. 平台基础架构

当前平台沿用既有代码审查平台框架：

| 层级 | 位置 | 说明 |
| --- | --- | --- |
| 前端 | `frontend/src` | React、Vite、TanStack Router 页面与路由 |
| 后端 | `backend/app` | FastAPI 路由、SQLModel 模型、服务层 |
| 数据库 | PostgreSQL | 存储用户、任务、状态、报告路径和统计字段 |
| 鉴权 | API Key 登录 | 登录后通过 `/api/v1/users/me` 获取当前用户和角色 |
| 存储 | 任务独立目录 | 每个任务保存 input、logs、reports 等文件 |

平台化功能不新建独立网站，不新建独立登录系统。新增能力应作为现有平台中的一个任务模块接入。

## 5. 任务管理入口设计

左侧菜单中的“任务管理”是统一的管理入口，目前包含：

- 代码审查任务管理：`/tasks/review`
- GPIO 配置表任务管理：`/tasks/gpio-manage`
- BOM 规格书匹配任务管理：`/tasks/bom-spec-compare-manage`
- 白盒测试任务管理：`/tasks/whitebox-manage`

任务管理页只负责查看和管理记录，不负责创建任务。创建任务保留在对应业务平台页面中，例如 GPIO 创建在 `/tasks/gpio`，BOM 创建在 `/tasks/bom-spec-compare`，白盒测试创建在 `/tasks/whitebox`。

这样区分后：

- 业务平台页面负责提交任务和查看自己的执行过程。
- 任务管理页面负责集中查看所有记录、输出和失败信息。
- 普通用户仍可使用同一页面，但只能看到自己的任务。

## 6. 权限规则

平台任务列表统一使用当前用户角色控制范围：

| 用户角色 | 可见范围 |
| --- | --- |
| `admin` | 查看所有人的任务记录、统计和输出 |
| `user` | 只能查看自己的任务记录、统计和输出 |

后端判断逻辑以 `has_admin_privileges(current_user)` 为准。当前实现中，GPIO、BOM、白盒测试和代码审查任务列表都遵守这套规则。

如果用户反馈“管理页只能看到自己的记录”，优先检查数据库中该用户的 `role` 字段是否为 `admin`。

## 7. 新平台复现开发流程

本节用于后续开发人员照着复现新增一个平台模块。

### 7.1 第一步：明确任务类型

先确认任务属于哪一种执行模式：

| 执行模式 | 适用场景 | 示例 |
| --- | --- | --- |
| 本地 Codex 模式 | 平台服务器可以直接执行任务 | GPIO 配置表、BOM 规格书匹配 |
| 远程 Agent 模式 | 任务必须在另一台电脑执行，例如依赖本地工具、许可证或测试环境 | 白盒测试 |
| 手动结果模式 | 暂时不能自动执行，只记录任务和上传结果 | 临时过渡任务 |

确认后再决定是否需要 Agent 相关接口。不要为了新平台重新做一套账号、数据库或存储规则。

### 7.2 第二步：设计任务表字段

任务表至少包含：

- `id`
- `user_id`
- 任务输入字段，例如 SVN 路径、版本号、上传文件信息
- `status`
- `input_files`
- `result_files` 或 `result_path`
- `error_message`
- `created_at`
- `started_at`
- `finished_at`
- `updated_at`

如果是远程 Agent 模式，还需要：

- `agent_id`
- Agent 心跳表
- Agent 领取任务、上传日志、上传报告相关接口

### 7.3 第三步：新增后端接口

每个任务模块建议提供以下接口：

```text
POST   /api/v1/<feature>-tasks
GET    /api/v1/<feature>-tasks
GET    /api/v1/<feature>-tasks/stats
GET    /api/v1/<feature>-tasks/{task_id}
GET    /api/v1/<feature>-tasks/{task_id}/report 或 /download
DELETE /api/v1/<feature>-tasks/{task_id}
```

列表和统计接口必须遵守统一权限规则：

```python
if has_admin_privileges(current_user):
    return all_tasks
return current_user_tasks
```

### 7.4 第四步：实现文件存储

任务文件按任务 ID 独立保存：

```text
<storage>/<task-id>/
  input/
  logs/
  reports/
```

上传文件、日志、报告都要能从任务记录追溯到真实路径。多文件输出优先打包成 zip 下载。

### 7.5 第五步：开发业务平台页

业务平台页用于提交任务，通常包含：

- 页面标题
- 新建任务表单
- 任务统计卡片
- 当前用户可见的任务列表
- 输出下载按钮
- 删除按钮

路径建议：

```text
/tasks/<feature>
```

### 7.6 第六步：开发任务管理页

任务管理页只负责查看和管理记录，不提供提交表单。

路径建议：

```text
/tasks/<feature>-manage
```

任务管理页应复用业务平台页里的统计组件和任务表格组件，只新增一个管理页组件导出。这样后续修改表格列、下载逻辑、删除逻辑时，只需要维护一套代码。

### 7.7 第七步：加入左侧菜单

菜单统一维护在：

```text
frontend/src/components/Sidebar/AppSidebar.tsx
```

平台入口和任务管理入口分开：

- 平台入口放在一级菜单，例如 `GPIO配置表平台`。
- 管理入口放在“任务管理”子菜单，例如 `GPIO配置表任务管理`。

### 7.8 第八步：新增路由文件

新增路由文件放在：

```text
frontend/src/routes/_layout/
```

示例：

```text
tasks.gpio.tsx
tasks.gpio-manage.tsx
```

构建时会自动更新：

```text
frontend/src/routeTree.gen.ts
```

一般不要手改 `routeTree.gen.ts`。

### 7.9 第九步：增加测试和验证

后端至少验证：

- 普通用户只能看自己的任务。
- 管理员可以看所有人的任务。
- 任务报告可以下载。
- 删除任务时记录和文件能同步删除。
- 统计接口返回正确数量。

前端至少验证：

```powershell
npm run build --workspace frontend
```

后端测试按模块执行：

```powershell
uv run pytest tests/api/routes/test_<feature>_tasks.py -q
```

## 8. 后端开发规则

新增任务模块时应包含：

1. 任务模型：保存提交人、输入信息、状态、输出文件、错误信息、时间字段。
2. 公开 schema：任务列表需要包含 `user_name` 和 `svn_username`。
3. 列表接口：管理员返回全部任务，普通用户按 `user_id` 过滤。
4. 统计接口：管理员统计全部任务，普通用户统计自己的任务。
5. 下载接口：使用 `FileResponse` 返回报告或压缩包。
6. 删除接口：删除任务记录时同步删除任务文件目录。

任务文件建议按如下结构存储：

```text
<storage>/<task-id>/
  input/
  logs/
  reports/
```

## 9. 前端开发规则

新增任务平台时应至少提供两个页面：

| 页面类型 | 用途 |
| --- | --- |
| 业务平台页 | 提交任务、查看当前任务列表和下载结果 |
| 任务管理页 | 只展示任务记录、状态、统计和输出，不提供提交表单 |

任务管理页优先复用业务平台页中的统计组件和任务表格组件，只新增一个管理页导出组件，避免同一类任务出现两套列表逻辑。

路由命名建议：

```text
/tasks/<feature>
/tasks/<feature>-manage
```

菜单入口统一维护在：

```text
frontend/src/components/Sidebar/AppSidebar.tsx
```

新增路由文件后，通过前端构建自动更新：

```text
frontend/src/routeTree.gen.ts
```

不要手工维护生成路由文件，除非构建器无法生成。

## 10. 常见问题处理

### 10.1 管理页只能看到自己的记录

原因通常是当前账号不是 `admin`。

处理方式：

1. 查询用户表中的 `role` 字段。
2. 将需要管理权限的账号设置为 `admin`。
3. 用户刷新页面；如果前端仍显示旧权限，退出后重新登录。

### 10.2 任务列表一直显示加载中

优先检查：

1. 前端 Vite 服务是否正常。
2. 后端接口是否返回 `200 OK`。
3. 浏览器是否仍缓存旧的 HMR 状态。

常见处理方式是重启前端 dev server，并让用户强制刷新页面。

### 10.3 任务成功但统计为 0

优先检查报告 JSON 结构是否与后端解析逻辑一致。BOM 规格书匹配曾出现过 7-3 中文字段格式未被统计解析的问题，已补充兼容：

- `project_count`
- `projects`
- `状态`
- `判定结论`
- `不一致`
- `BOM有规格书无`
- `规格书有BOM无`

后续如果报告格式变化，应先增加回归测试，再修复解析逻辑。

## 11. 新增平台检查清单

开发新平台时，按下面清单逐项确认：

- [ ] 是否复用现有账号和 API Key 登录。
- [ ] 是否明确执行模式：本地 Codex、远程 Agent 或手动结果。
- [ ] 是否新增任务模型和公开 schema。
- [ ] 任务公开 schema 是否包含 `user_name` 和 `svn_username`。
- [ ] 列表接口是否实现 admin 全量、user 只看自己的权限规则。
- [ ] 统计接口是否使用相同权限规则。
- [ ] 下载接口是否能返回实际输出文件。
- [ ] 删除接口是否同步清理任务文件。
- [ ] 是否有业务平台页 `/tasks/<feature>`。
- [ ] 是否有任务管理页 `/tasks/<feature>-manage`。
- [ ] 是否把管理页加入“任务管理”菜单。
- [ ] 是否运行后端接口测试。
- [ ] 是否运行前端构建。
- [ ] 是否手动访问页面确认能加载任务列表。

## 12. 后续维护建议

1. 新增平台时先判断执行模式：本地 Codex 或远程 Agent。
2. 管理页和业务页分开，但复用同一个任务表格组件。
3. 所有任务列表必须显示提交人、状态、时间、关键输入、输出下载和失败原因。
4. 管理员全量查看、普通用户只看自己，这条规则保持一致。
5. 每次修改任务解析、统计或下载逻辑后，都要跑对应后端测试和前端构建。
