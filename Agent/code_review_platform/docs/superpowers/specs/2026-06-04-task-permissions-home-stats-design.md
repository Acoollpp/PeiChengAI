# 任务权限与主页统计设计

## 背景

`code_review_server` 当前有两类相关功能：

- Web 前端左侧菜单把普通用户带到 `仪表盘` 和 `部门管理`。
- 代码审查任务管理页面位于 `/admin/tasks/review`，只能通过管理员路由访问。

后端 `GET /api/v1/review-tasks` 已经按权限过滤数据：普通用户只能读取 `current_user.id` 创建的任务，管理员和超管可以读取全部任务。任务详情、报告读取、报告下载、状态更新和删除也复用同样的权限判断。

本次目标是修正普通用户的可见功能：普通用户应能管理自己的代码审查任务，不能看到部门管理；管理员仍然能看到部门管理，并且任务和首页统计按管理员范围展示全量汇总。

## 目标

1. 将 `仪表盘` 改名为 `主页`。
2. 普通用户菜单只显示 `主页` 和 `任务管理`。
3. 管理员菜单显示 `主页`、`部门管理`、`用户管理`、`任务管理`、`Skill库`。
4. 普通用户不能通过菜单或直接访问 `/items` 打开部门管理页面。
5. 代码审查任务管理页面改成普通用户和管理员都能访问的通用页面。
6. 普通用户在任务管理中只能看到、打开报告、下载报告和删除自己账号提交的任务。
7. 管理员在任务管理中可以看到所有用户任务，并保留用户姓名和 SVN 账号筛选。
8. 主页增加任务数量统计，普通用户只统计自己的任务，管理员统计所有任务。

## 非目标

1. 不修改任务创建、状态更新、报告上传和报告文件存储流程。
2. 不重做部门管理模型或后端部门接口语义。
3. 不在第一版加入复杂时间趋势、用户排行或部门维度统计。
4. 不引入新的图表库；状态数量图使用现有 React、Tailwind 和基础 UI 组件实现。
5. 不改变 CCH 同步、用户管理和 Skill 管理的权限模型。

## 当前实现约束

当前前端结构如下：

- `AppSidebar.tsx` 定义左侧菜单。`baseItems` 目前包含 `仪表盘` 和 `部门管理`，因此普通用户会看到部门管理。
- `/items` 是部门管理页面，目前没有管理员路由守卫。
- `/admin` 路由通过 `requireAdminUser()` 校验管理员权限。
- `/admin/tasks/review` 渲染 `AdminTasksPage`，因此普通用户无法访问任务管理页面。
- 主页路由 `/_layout/index.tsx` 目前只有欢迎语，没有统计数据。
- `AdminTasksPage` 内部直接用 `fetch` 调用 `/api/v1/review-tasks`，包含任务表、筛选、报告打开、报告下载和删除。

当前后端结构如下：

- `has_admin_privileges()` 判断 `is_superuser` 或 `role == admin`。
- `read_review_tasks()` 对普通用户追加 `ReviewTask.user_id == current_user.id` 过滤。
- `_get_task_for_user()` 对非管理员访问非本人任务返回 403。
- 测试已经覆盖普通用户不能读/删其他用户任务、管理员能读全量任务、普通用户筛选只搜索本人任务。

## 方案选择

采用通用任务管理页面方案：

1. 将代码审查任务管理从管理员专属页面迁移或复用到 `/tasks/review`。
2. 前端菜单按角色显示不同入口。
3. 任务列表继续调用同一个后端接口，由后端决定返回本人任务还是全量任务。
4. 任务页面根据当前用户角色显示不同筛选能力。
5. 主页新增后端统计接口，由后端按同样权限口径统计任务数量。

该方案复用现有后端权限保护，避免维护两套任务页面，也避免放松 `/admin` 路由语义。

## 路由和菜单设计

### 普通用户菜单

普通用户左侧菜单显示：

- `主页`，路径 `/`
- `任务管理`
  - `代码审查任务管理`，路径 `/tasks/review`

普通用户不显示 `部门管理`、`用户管理`、`Skill库`。

### 管理员菜单

管理员左侧菜单显示：

- `主页`，路径 `/`
- `部门管理`，路径 `/items`
- `用户管理`，路径 `/admin/users`
- `任务管理`
  - `代码审查任务管理`，路径 `/tasks/review`
- `Skill库`，路径 `/admin/skills`

管理员不再需要通过 `/admin/tasks/review` 访问任务管理。为了兼容已有链接，保留 `/admin/tasks/review` 路由并重定向到 `/tasks/review`；普通用户仍不能进入 `/admin` 路由。

### 部门管理访问控制

`/items` 页面增加管理员守卫：

- 非登录用户仍按全局布局守卫跳到 `/login`。
- 普通用户访问 `/items` 时重定向到 `/`。
- 管理员可以正常访问 `/items`。

本次主要收紧前端可见性和页面访问。后端 items 接口当前用于模板项目的 owner 模型，是否改成管理员专属接口不纳入本次范围，避免误伤已有数据语义。

## 任务管理页面设计

任务管理页面使用同一个组件，但根据当前用户角色切换文案和筛选项。

### 普通用户视图

普通用户页面标题仍为 `代码审查任务管理`，说明文案强调查看自己提交的代码审查任务。

普通用户隐藏以下筛选：

- 用户姓名
- SVN 账号

任务表保留：

- 用户名称
- SVN 账号
- SVN 地址
- 版本
- 状态
- 执行客户端
- 报告
- 操作

普通用户看到的用户名称和 SVN 账号只会是自己。保留这些列有助于和管理员视图保持表格结构一致，也方便确认任务归属。

普通用户可执行：

- 打开自己的报告。
- 下载自己的报告。
- 删除自己的任务。

后端已经阻止普通用户操作其他用户任务。

### 管理员视图

管理员页面继续显示用户姓名和 SVN 账号筛选。

管理员任务列表显示所有用户任务，并保留现有操作：

- 打开报告。
- 下载报告。
- 删除任务。

管理员筛选仍通过 `user_name` 和 `svn_username` 查询参数传给 `/api/v1/review-tasks`。

## 主页统计设计

主页保留欢迎语，并新增任务数量统计区域。

统计区域包含：

1. 汇总数字卡片：
   - 总任务数。
   - 成功数。
   - 失败/异常数。
   - 运行中数。
2. 状态数量图：
   - 使用横向条形图展示每个任务状态的数量。
   - 每个状态固定展示，即使数量为 0 也展示为 0。
   - 使用中文状态名。

状态中文名：

- `created`: `待处理`
- `checking_environment`: `环境检查中`
- `running_codex`: `运行中`
- `uploading_report`: `上传报告中`
- `success`: `成功`
- `failed`: `失败`
- `environment_error`: `环境异常`
- `cancelled`: `已取消`

运行中数由以下状态合计：

- `checking_environment`
- `running_codex`
- `uploading_report`

失败/异常数由以下状态合计：

- `failed`
- `environment_error`
- `cancelled`

该图比时间趋势更适合第一版，因为当前最重要的问题是任务总量和任务卡在哪些状态，而不是趋势分析。

## 统计接口设计

新增接口：

```text
GET /api/v1/review-tasks/stats
```

响应结构：

```json
{
  "total": 12,
  "success": 7,
  "running": 2,
  "failed_or_error": 3,
  "by_status": {
    "created": 1,
    "checking_environment": 0,
    "running_codex": 2,
    "uploading_report": 0,
    "success": 7,
    "failed": 1,
    "environment_error": 1,
    "cancelled": 1
  }
}
```

权限口径：

- 普通用户只统计 `ReviewTask.user_id == current_user.id` 的任务。
- 管理员和超管统计所有任务。

接口应返回所有状态键，缺失状态补 0，便于前端稳定渲染。

## 数据流

### 任务管理

1. 用户打开 `/tasks/review`。
2. 页面读取当前用户信息，判断是否有管理员权限。
3. 页面调用 `GET /api/v1/review-tasks`。
4. 后端按当前用户权限返回本人任务或全量任务。
5. 管理员提交筛选时追加 `user_name` 和 `svn_username` 查询参数。
6. 普通用户不渲染筛选项，因此不会发出用户维度筛选。
7. 打开报告、下载报告和删除任务继续调用现有接口。

### 主页统计

1. 用户打开 `/`。
2. 页面调用 `GET /api/v1/review-tasks/stats`。
3. 后端按当前用户权限聚合任务数量。
4. 前端渲染汇总卡片和状态条形图。
5. 如果统计加载失败，只在统计区域显示错误提示，欢迎语仍正常显示。

## 错误处理

- 任务列表加载失败时沿用现有加载失败处理。
- 删除任务失败时沿用现有 toast 提示。
- 报告打开或下载失败时沿用现有错误处理。
- 统计接口失败时，主页统计区域显示轻量错误提示，不阻塞页面其他内容。
- 统计接口返回空数据时，前端展示总数和各状态数量为 0。

## 测试计划

### 后端测试

新增或扩展 `test_review_tasks.py`：

1. 普通用户调用 `/review-tasks/stats` 只统计自己的任务。
2. 管理员或超管调用 `/review-tasks/stats` 统计所有用户任务。
3. 统计响应包含所有 `ReviewTaskStatus` 键，未出现的状态为 0。
4. 运行中、失败/异常汇总字段符合状态分组。

### 前端测试

根据现有测试模式补充 Playwright 或组件级验证：

1. 普通用户菜单不出现 `部门管理`，出现 `主页` 和 `任务管理`。
2. 管理员菜单出现 `部门管理`。
3. 普通用户访问 `/items` 被重定向到 `/`。
4. 普通用户任务管理页面不显示用户姓名和 SVN 账号筛选。
5. 管理员任务管理页面显示用户姓名和 SVN 账号筛选。
6. 主页展示统计卡片和状态条形图，空数据为 0。

## 验收标准

1. 普通用户登录后左侧菜单没有 `部门管理`。
2. 普通用户能从左侧菜单进入 `任务管理` 并看到自己提交的代码审查任务。
3. 普通用户无法通过 `/items` 打开部门管理页面。
4. 管理员登录后左侧菜单仍有 `部门管理`。
5. 管理员能进入任务管理并查看所有用户任务。
6. `仪表盘` 文案改为 `主页`，页面标题和浏览器标题同步更新。
7. 主页展示任务数量统计图；普通用户统计自己，管理员统计全量。
8. 后端测试能证明统计接口不会向普通用户泄漏其他用户任务数量。
