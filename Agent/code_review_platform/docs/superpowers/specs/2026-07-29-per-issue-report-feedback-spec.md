# 逐问题报告反馈与最终 PDF 正式规格

## 问题陈述

当前系统只能让用户对整份代码审查报告提交一次“有帮助”或“没帮助”的报告级反馈。当一份报告包含多个审查问题时，系统无法分别记录每个问题是否有帮助、用户对该问题的补充说明，也无法稳定导出逐问题明细。

客户需要把反馈粒度细化到单个审查问题。用户完成反馈后取得的 PDF 报告还需要包含每个问题的评价和反馈说明，以便上传到项目管理系统并保留处理过程。同时，原始 Markdown 必须保持为不可变的 AI 审查结果，不能因为用户反馈而被覆盖。

现有报告已经进入使用流程，不能因新功能被重新解析、迁移或改变。因此，新流程只适用于功能上线后按新协议生成的报告，并继续兼容历史报告的报告级反馈与已有 PDF。

## 解决方案

新报告生成后，Electron 客户端从最终原始 Markdown 中识别全部审查问题，并将每个问题的问题原文、描述原文、顺序和定位信息作为快照随报告提交到服务端。服务端为每个问题保存一条独立记录，并以协议版本区分新报告和历史报告。

用户在 Electron 客户端点击“提交反馈并查看 PDF 报告”后进入逐问题反馈窗口。每个问题必须选择“有帮助”或“没帮助”，并填写反馈说明；填写过程按问题自动保存为服务端草稿，草稿阶段允许说明暂时为空。全部问题完成评价并填写说明后，客户端在内存中把“是否有帮助”和“用户反馈”插入对应问题下方，生成并上传唯一一份最终 PDF。只有 PDF 上传成功后，服务端才把反馈锁定为已提交；任何失败都保留可编辑草稿。

本地和远程原始 Markdown 均不写入反馈，也不保存第二份反馈版 Markdown。提交后，客户端提供“查看已提交反馈”和“查看 PDF 报告”入口。Web 任务管理增加桌面端任务详情能力，展示反馈进度、逐问题只读详情和 Excel 导出，不新增一级菜单。

## 用户故事

1. 作为代码审查任务提交人，我希望新报告中的每个审查问题都能独立反馈，以便准确表达哪些问题有帮助、哪些问题没有帮助。
2. 作为代码审查任务提交人，我希望看到每个问题的问题原文和描述原文，以便确认自己正在评价的具体问题。
3. 作为代码审查任务提交人，我希望每个问题可以互斥选择“有帮助”或“没帮助”，以便系统获得明确的问题评价。
4. 作为代码审查任务提交人，我希望尚未选择的问题显示为“未评价”，以便识别仍需处理的项目。
5. 作为代码审查任务提交人，我希望每个问题正式提交前必须填写反馈说明，以便稳定记录帮助点、处理情况、无帮助原因或具体说明。
6. 作为代码审查任务提交人，我希望“有帮助”的输入框提示可以引导填写帮助点或处理情况，以便更容易留下有价值的说明。
7. 作为代码审查任务提交人，我希望“没帮助”的输入框提示可以引导填写原因和具体说明，以便更容易说明问题所在。
8. 作为代码审查任务提交人，我希望问题评价变更后自动保存，以便不需要逐项点击保存。
9. 作为代码审查任务提交人，我希望停止输入或离开输入框后自动保存反馈说明，以便填写过程保持连贯。
10. 作为代码审查任务提交人，我希望自动保存正常时不出现打断操作的提示，以便专注完成反馈。
11. 作为代码审查任务提交人，我希望自动保存失败时保留当前输入并显示可重试状态，以便网络异常不会导致内容丢失。
12. 作为代码审查任务提交人，我希望关闭反馈窗口或重启客户端后可以恢复已保存草稿，以便分多次完成反馈。
13. 作为代码审查任务提交人，我希望存在未评价问题时不能正式提交，并自动定位到第一个未评价问题，以便避免遗漏。
14. 作为代码审查任务提交人，我希望正式提交前系统等待所有自动保存完成，以便最终 PDF 使用最新反馈。
15. 作为代码审查任务提交人，我希望任务完成时先得到原始 Markdown，而不是提前生成无反馈 PDF，以便最终只保留一份有效 PDF。
16. 作为代码审查任务提交人，我希望点击“提交反馈并查看 PDF 报告”后生成包含反馈的最终 PDF，以便直接上传到项目管理系统。
17. 作为代码审查任务提交人，我希望最终 PDF 在每个问题对应位置显示“是否有帮助”和“用户反馈”，以便阅读者可以把反馈与问题直接对应起来。
18. 作为代码审查任务提交人，我希望未填写反馈说明时系统阻止正式提交，并定位到第一个缺失问题，以便及时补全。
19. 作为代码审查任务提交人，我希望 PDF 生成或上传失败时反馈仍保持草稿且可以重试，以便不会出现反馈被锁定但没有正式 PDF 的状态。
20. 作为代码审查任务提交人，我希望提交成功后自动打开最终 PDF，以便立即检查和使用报告。
21. 作为代码审查任务提交人，我希望已提交反馈不可直接修改，以便已上传到项目管理系统的 PDF 与系统记录保持一致。
22. 作为代码审查任务提交人，我希望提交后可以只读查看全部已提交反馈，以便追溯当时的评价和说明。
23. 作为代码审查任务提交人，我希望提交后可以再次查看最终 PDF，以便后续下载或查阅。
24. 作为代码审查任务提交人，我希望原始本地 Markdown 不被用户反馈改写，以便保留 AI 的原始审查输出。
25. 作为平台管理员，我希望远程保存的原始 Markdown 不被用户反馈改写，以便审计时能够还原原始报告。
26. 作为代码审查任务提交人，我希望新报告不显示本机 Markdown 输出路径，以便报告中不泄露无业务价值的本地路径信息。
27. 作为代码审查任务提交人，我希望报告中的相对图片在最终 PDF 中仍能正常显示，以便带截图或图示的问题保持完整。
28. 作为普通 Web 用户，我希望在任务列表看到自己新报告的反馈进度，以便快速判断反馈是否完成。
29. 作为部门管理员，我希望在权限范围内查看本部门任务的反馈进度和逐问题详情，以便了解团队反馈情况。
30. 作为系统管理员，我希望查看全部任务的反馈进度和逐问题详情，以便统一管理反馈数据。
31. 作为 Web 用户，我希望从任务管理进入任务详情，而不是增加新的一级菜单，以便现有导航保持简洁。
32. 作为 Web 用户，我希望在任务详情中切换“问题反馈”和“原始报告”，以便在同一任务上下文中核对反馈和原始内容。
33. 作为 Web 用户，我希望任务详情只读，以便管理端查看不会改变任务提交人的正式反馈。
34. 作为有权限的 Web 用户，我希望下载最终 PDF，以便归档或上传到其他业务系统。
35. 作为有权限的 Web 用户，我希望导出权限范围内的逐问题反馈 Excel，以便开展后续统计与分析。
36. 作为反馈数据分析人员，我希望 Excel 一行对应一个审查问题，以便直接进行问题分类和汇总。
37. 作为反馈数据分析人员，我希望 Excel 保留提交人、日期、SVN 信息、问题原文、描述原文、评价和反馈说明，以便后续 AI 获得完整分析上下文。
38. 作为反馈数据分析人员，我希望导出只包含新逐问题协议报告，以便不会把旧报告级反馈误当成逐问题数据。
39. 作为平台维护者，我希望历史任务继续使用原有反馈和 PDF 展示逻辑，以便上线新功能不会改变既有数据和用户记录。
40. 作为旧版本客户端用户，我希望原有报告级反馈接口继续可用，以便后端升级期间客户端仍能正常工作。
41. 作为平台维护者，我希望无法识别审查问题的报告不会生成虚假问题记录，以便反馈数据保持真实。
42. 作为平台维护者，我希望只有任务提交人可以在 Electron 客户端保存或正式提交问题反馈，以便他人不能篡改反馈。
43. 作为平台维护者，我希望重复保存同一问题时更新原草稿而不是产生重复记录，以便问题与反馈保持一对一。
44. 作为反馈数据分析人员，我希望后续 AI 可以基于导出数据估算效率提升、代码品质提升和人工不易发现的问题，以便形成改进参考。
45. 作为反馈数据使用者，我希望上述效率和品质结果明确标识为估算而非真实测量，以便避免错误解读。

## 实施决策

- 新逐问题反馈只适用于功能上线后使用新协议生成的报告。历史任务不迁移、不重新解析，也不自动创建问题记录。
- 审查任务通过可空的反馈协议版本区分新旧流程，并记录正式提交时间。没有协议版本的任务继续使用历史报告级反馈。
- 服务端新增审查问题实体，一份审查任务包含零个或多个审查问题，每个问题独立保存问题原文、描述原文、展示快照、顺序、定位信息、问题评价、反馈说明和审计时间。
- 服务端生成稳定的问题 ID。客户端定位信息只用于当前不可变原始 Markdown 的反馈合成，不作为长期业务身份。
- 问题评价有“未评价”“有帮助”“没帮助”三种状态；正式提交要求每个问题均为“有帮助”或“没帮助”，且反馈说明去除首尾空白后非空。草稿自动保存仍允许说明为空。
- Electron 从最终原始 Markdown 中提取问题快照，报告预览、高亮、反馈窗口和最终 PDF 合成共用同一问题识别结果，避免不同入口对问题边界理解不一致。
- 模板一以叶子问题标题作为问题边界，问题原文取标题，描述原文优先取问题描述、缺陷描述或不合规现象描述等字段。
- 模板二优先以有效问题表格行作为问题边界，问题原文由风险等级和专项方向组成，描述原文取缺陷描述相关内容；没有有效表格行时使用结论列表项兜底。
- 新报告上传时同时提交问题快照和原始 Markdown 引用的相对图片资产。资产只允许位于报告的相对图片目录中，禁止绝对路径和目录穿越。
- 启动审查任务的内部提示继续包含 Markdown 写入路径和图片目录，但报告正文不得显示本地输出路径。上传前对残留的报告输出路径字段进行精确清理。
- 原始 Markdown 在上传后保持不可变。本地原始 Markdown 和远程原始 Markdown 均不写入反馈，不保存第二份反馈版 Markdown。
- Electron 工具栏在新报告提交前显示“提交反馈并查看 PDF 报告”；提交后显示“查看已提交反馈”和“查看 PDF 报告”。历史任务保留旧入口。
- 反馈窗口逐问题展示问题原文、描述原文、互斥的问题评价和必填反馈说明。具体控件样式可以遵循现有桌面端设计系统，但不得改变三态语义。
- 问题评价变更后立即乐观更新并自动保存；反馈说明停止输入约一秒或失焦后自动保存。正常保存保持安静，失败时保留输入并允许重试。
- 正式提交前必须校验所有问题已评价、反馈说明均非空，并等待所有草稿请求成功完成。
- 正式提交时，Electron 在内存渲染稿中把“是否有帮助”和“用户反馈”插入对应问题末尾，再使用原始报告的相对图片生成本地最终 PDF。
- 模板一在问题内容末尾、下一问题标题或分隔线之前插入反馈。模板二在对应问题表格行的内容末尾插入反馈，不增加新的宽表格列。
- 草稿阶段反馈说明可以为空并继续自动保存，但不得生成或上传最终 PDF。
- 每个任务只生成并保存一份最终 PDF。任务完成阶段不提前生成 PDF，也不把没有反馈的临时 PDF 上传到服务端。
- 最终 PDF 上传和反馈锁定属于同一个业务完成动作。服务端只有在确认所有问题已评价、反馈说明均非空且 PDF 保存成功后才记录正式提交时间。
- PDF 生成失败、图片资产缺失、上传失败或服务端校验失败时，反馈保持为可编辑草稿，不产生已提交状态。
- 已提交反馈不可修改。本期不提供修改入口、修改申请、审批或修订版 PDF。
- 客户端只读回看复用反馈窗口，只显示问题、评价、反馈说明和提交时间，不显示输入控件或提交命令。
- 历史已提交但反馈说明为空的逐问题记录不迁移，继续允许只读回看并显示“未填写”。
- Web 在现有任务管理下增加桌面端任务详情，不增加一级侧边栏菜单。任务列表显示新报告的反馈进度和状态，详情提供“问题反馈”和“原始报告”视图、最终 PDF 入口。
- Web 端只读。普通用户只能查看自己的任务，部门管理员可以查看本部门任务，系统管理员可以查看全部任务；只有任务提交人可以通过 Electron 写入反馈。
- Excel 导出遵循当前用户的数据权限范围，工作表名称为“问题反馈明细”，一行对应一个新协议审查问题。
- Excel 固定包含九列：提交人、日期、SVN路径、旧版本号、新版本号、AI报告问题原文、问题描述原文、是否有帮助、审查问题反馈。
- Excel 中未评价的问题显示“未反馈”，未填写的反馈说明保持空单元格。历史报告级反馈不进入该导出。
- 报告没有识别到有效问题时不创建虚假记录，允许用户直接生成不带反馈块的最终 PDF。
- 后端先部署兼容的数据结构和接口，再发布支持逐问题反馈的新 Electron 客户端，最后发布 Web 任务详情和导出入口。升级期间保留旧客户端所需的报告级反馈接口。

## 测试决策

- 测试只验证用户或跨进程接口能够观察到的行为，不直接断言内部函数、私有状态、具体文件布局或实现步骤。
- 后端以现有审查任务 API 路由测试为主要边界，使用真实测试数据库和临时报告存储验证：新报告问题快照创建、草稿幂等保存、读取权限、全部评价校验、PDF 成功后锁定、失败后保持草稿、提交后冲突、历史任务兼容、任务删除清理和九列 Excel 导出。
- Electron 以现有反馈窗口组件、IPC、任务执行、报告上传和 PDF 生成测试为主要边界，验证从“提交反馈并查看 PDF 报告”到最终 PDF 打开的完整桌面流程，包括草稿恢复、自动保存失败重试、未评价阻止提交、反馈插入正确问题、原始 Markdown 字节不变、图片加载、仅生成一份 PDF 和失败后可重试。
- Web 以现有任务管理 Playwright 测试为主要边界，仅验证桌面端：任务列表反馈进度、任务详情导航、逐问题只读展示、权限范围、原始报告与最终 PDF 入口、Excel 导出，以及页面在目标桌面视口下不存在内容遮挡或异常横向溢出。
- 模板一和模板二都必须使用包含多个问题的代表性 Markdown 固件，覆盖标题型问题、表格行问题、结论列表兜底、空说明草稿、中文文本和相对图片。
- 兼容性测试必须证明历史任务不会生成问题记录，不改变旧报告级反馈，不改变已有 Markdown 和 PDF 下载行为。
- 正式提交的故障测试必须覆盖 PDF 生成失败、图片缺失、PDF 上传失败和重复提交，证明服务端不会提前锁定反馈。
- 功能完成后分别运行后端测试、Electron 单元与集成测试、Web Playwright 桌面测试及各项目的类型检查和构建；最后运行完整测试集。

## 范围之外

- 不迁移、重新解析或补录功能上线前的历史报告。
- 不改变历史报告级反馈、历史 Markdown 或历史 PDF。
- 不强制用户填写帮助点、处理结果、无帮助原因、原因分类或其他结构化补充字段。
- 不实现已提交反馈的编辑、修改申请、审批流程或修订版 PDF。
- 不保存反馈版 Markdown，也不修改本地或远程原始 Markdown。
- 不在本期直接实现问题细节分类、效率提升估算、代码品质提升估算或人工审查难度推断；这些能力由后续独立 AI 基于导出表实现。
- 不把后续 AI 产生的效率或品质估算描述为真实人工审查效率或真实代码质量测量值。
- 不新增 Web 一级菜单。
- 不实现或验证 Web 移动端布局；本期 Web 范围仅包含桌面端。
- 不允许 Web 管理端代替任务提交人填写或修改问题反馈。

## 补充说明

- 领域术语以仓库根目录的领域上下文文档为准。
- 原始 Markdown 与反馈版 PDF 的不可变边界以“仅在最终 PDF 中合成问题反馈”的架构决策为准。
- 本规格的后续工作应使用 `to-tickets` 拆成能够独立演示和验证的纵向 Issue，并声明阻塞关系；每个可执行 Issue 再单独使用 `implement` 完成。
