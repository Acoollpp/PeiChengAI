# Electron 并发任务队列设计

## 背景

当前 Electron 客户端一次只能顺畅执行一个代码审查任务。表单提交后会等待 `executeTask()` 返回，提交按钮在此期间处于“审查中”状态；任务看板也把 `tasks[0]` 作为唯一“当前任务”，其余任务作为历史任务展示。

从主进程实现看，审查任务已经按服务端 `taskId` 创建独立工作区、报告路径和图片目录，Codex 执行也通过独立子进程启动。因此并发能力不是 Codex CLI 或工作区结构上的根本限制，而是当前客户端缺少本地任务调度、队列状态和多任务看板语义。

## 目标

1. Electron 客户端支持最多 2 个代码审查任务同步执行。
2. 用户可以不限数量连续提交任务，超过并发上限的任务进入本地等待队列。
3. 第一版队列只在客户端运行期间有效，不做重启恢复。
4. 保留现有任务看板功能，包括任务摘要、状态、进度、Codex 日志、错误信息、查看报告、报告位置和选中态。
5. 保持服务端任务模型稳定，第一版不新增数据库状态和迁移。
6. 并发任务之间的进度、日志、报告预览和报告位置不能串任务。

## 非目标

1. 不实现客户端关闭后的队列恢复。
2. 不把排队任务提前持久化到服务端。
3. 不新增服务端 `queued` 状态。
4. 不实现后台统一调度多个客户端的任务。
5. 不增加任务优先级、暂停、恢复或拖拽排序。
6. 不处理截图上传能力；截图相关功能沿用其他分支的实现计划。

## 方案选择

采用客户端内存队列方案：

1. 渲染进程接收用户提交，立即创建本地任务记录。
2. 本地调度器维护 `queued`、`running`、`finished` 三类任务。
3. 同时运行任务数小于 2 时，调度器自动启动等待队列里的下一个任务。
4. 任务真正开始执行时才调用现有 `window.codeReview.executeTask()`，由主进程创建服务端任务并执行 Codex。
5. 任务执行完成后，调度器释放运行槽位并启动下一条等待任务。

该方案改动集中在 Electron 客户端，对服务端和管理后台影响最小。未开始的等待任务不创建服务端记录，因此客户端关闭后不会在服务端留下长期 `created` 状态的半成品任务。

## 任务状态设计

共享服务端状态保持不变：

- `created`
- `checking_environment`
- `running_codex`
- `uploading_report`
- `success`
- `failed`
- `environment_error`
- `cancelled`

Electron 渲染进程额外使用本地展示状态：

```ts
type LocalTaskQueueState = 'queued' | 'starting' | 'running' | 'finished'
```

`queued` 只存在于客户端内存，不上传服务端。看板文案展示为“等待中”。当任务从队列进入执行时，状态先显示为“启动中”，随后由现有进度事件更新为 `checking_environment`、`running_codex`、`uploading_report` 等服务端状态。

为避免污染共享类型，可以在渲染层定义本地类型：

```ts
type TaskViewItem = ReviewTask & {
  localQueueState?: LocalTaskQueueState
  localTaskId?: string
  queueIndex?: number
}
```

服务端返回的历史任务仍使用 `ReviewTask` 原始结构。

## 调度器设计

新增一个渲染层队列控制模块或 hook，例如 `useTaskQueue`。它负责：

- 保存本地任务列表。
- 接收提交 payload 并创建本地任务。
- 控制最多 2 个任务执行。
- 调用 `window.codeReview.executeTask(payload)`。
- 处理任务成功、失败和环境异常。
- 将服务端返回的真实 `taskId` 回填到本地任务。
- 按 `taskId` 或 `localTaskId` 归属进度事件。
- 在任务结束后自动启动下一条等待任务。

并发上限作为常量定义：

```ts
const MAX_CONCURRENT_REVIEW_TASKS = 2
```

第一版不做用户可配置，避免扩大范围。

### 提交流程

1. 用户填写表单并点击“开始审查”。
2. 表单只校验字段和模板可用性，不等待整个 Codex 审查完成后才恢复。
3. 页面立即生成 `localTaskId`，插入任务列表。
4. 如果当前运行数小于 2，立即启动该任务。
5. 如果当前运行数已经是 2，该任务保留在等待队列，显示排队序号。

表单按钮文案不再长时间显示“审查中...”。它只在本次提交入队过程中短暂显示“提交中...”，入队成功后恢复可点击。

### 执行流程

任务开始执行时调用现有 `executeTask()`。主进程继续执行现有流程：

1. 同步 Skill。
2. 创建服务端任务。
3. 检查本机环境。
4. 准备任务工作区。
5. 启动 Codex。
6. 上传报告。
7. 返回报告 Markdown 和本地报告路径。

渲染进程收到结果后：

- 将本地任务 ID 替换或绑定为真实服务端 `taskId`。
- 更新最终状态。
- 成功时保存 `report_path`，并在右侧报告预览中只展示当前选中任务的报告。
- 失败时保存错误摘要。
- 释放一个运行槽位，启动队列中的下一条任务。

## 任务看板设计

任务看板从原来的“当前任务 / 历史任务”升级为三个分区：

1. `运行中`
2. `等待中`
3. `历史任务`

### 运行中

运行中分区展示最多 2 个正在执行或启动中的任务。每个任务卡保留现有当前任务能力：

- 任务 ID 或本地临时 ID。
- SVN 地址。
- 旧版本号。
- 新版本号。
- 审查模板。
- 当前状态。
- 进度消息。
- Codex 实时日志。
- 错误信息。
- 成功后的“查看报告”按钮。

Codex 日志必须按任务独立保存，不能使用“任意 local 任务”兜底匹配。进度事件应优先用真实 `taskId` 匹配；任务刚创建但真实 ID 尚未回填时，需要通过启动 Promise 持有的本地任务上下文完成绑定。

### 等待中

等待中分区展示所有已提交但尚未开始执行的任务。每个任务卡展示：

- 排队序号。
- SVN 地址。
- 旧版本号。
- 新版本号。
- 审查模板。
- 状态“等待中”。

第一版不提供“取消等待”按钮，只展示等待状态。取消队列属于后续增强，避免第一版引入额外的任务删除、撤销和边界状态。

### 历史任务

历史任务不再通过 `tasks.slice(1)` 得出，而是由终态任务组成：

- `success`
- `failed`
- `environment_error`
- `cancelled`

历史任务继续保留现有能力：

- 成功任务显示“查看报告”。
- 失败或环境异常任务显示错误信息。
- 不展示 Codex 实时日志，保持列表紧凑。

页面初次加载的服务端任务列表会进入历史任务或运行中展示，具体取决于服务端状态。由于第一版不做重启恢复，加载到的旧运行态任务如果实际已经因客户端关闭而停止，应按服务端当前状态展示，不自动续跑。

## 报告预览和报告位置

右侧 Markdown 报告预览继续作为单报告视图，但必须明确绑定 `selectedTaskId`。

规则：

1. 用户点击某个成功任务的“查看报告”，右侧预览该任务报告。
2. 某个运行中任务成功完成时，如果当前没有选中报告，可以自动预览该任务报告。
3. 如果用户已经手动选中其他任务报告，新完成任务不能强行覆盖右侧预览。
4. “查看报告位置”优先使用 `selectedTaskId` 对应的报告路径。
5. 如果选中任务没有本地报告路径，则沿用现有下载逻辑，从服务端读取报告后写入本地路径并打开位置。

主进程中 `latestSuccessfulReport` 的语义需要弱化，避免并发时打开最后完成但非当前选中的报告。IPC 已支持传入 `taskId`，渲染层应总是传入当前选中任务 ID。

## 错误处理

### 单任务失败

单个任务失败只影响该任务：

- 任务状态更新为 `failed` 或 `environment_error`。
- 错误信息展示在对应任务卡。
- 调度器释放运行槽位。
- 队列继续启动下一条任务。

### Skill 同步或环境失败

每个任务开始执行时仍走现有 Skill 同步和环境检查。若失败，该任务进入失败或环境异常，不阻塞后续任务永久等待。后续任务开始时会重新检查环境。

### 客户端关闭

第一版不做恢复：

- 尚未开始的等待任务只存在内存中，关闭后丢失。
- 正在执行的 Codex 子进程随客户端退出而终止，服务端可能停留在最后一次上报状态。
- 下次打开客户端不自动续跑旧任务。

为了减少误解，等待队列区域可以使用简短提示：

```text
等待任务仅在本次客户端运行期间保留。
```

### 进度事件错配

当前 `applyTaskProgress()` 里通过 `task.id === event.taskId || task.id.startsWith('local-')` 匹配任务。并发后必须移除这种宽松匹配，改成明确映射：

- `serverTaskId -> localTaskId`
- `localTaskId -> serverTaskId`

只有匹配到对应任务才更新进度和日志。

## 组件边界

### TaskPage

`TaskPage` 继续负责页面级状态和报告预览，但不直接承担并发调度细节。它使用 `useTaskQueue` 获得：

- `tasks`
- `runningTasks`
- `queuedTasks`
- `historyTasks`
- `submitTask`
- `applyProgressEvent`

### useTaskQueue

`useTaskQueue` 是并发调度的核心边界，负责本地队列和执行生命周期。它不渲染 UI，只管理状态和副作用。

### TaskBoard

`TaskBoard` 负责展示三个分区。它不直接调用 `executeTask()`，只接收任务数据和回调：

- `onViewReport(task)`

### TaskForm

`TaskForm` 保留输入和模板选择职责。提交后只等待入队动作完成，不等待审查完成。

## 数据流

1. 页面加载时调用 `listTasks()` 获取服务端任务列表。
2. 服务端任务进入历史或运行态展示，但第一版不自动续跑旧任务。
3. 用户提交任务，`useTaskQueue.submitTask()` 创建本地队列项。
4. 调度器判断是否有空闲运行槽位。
5. 有空闲槽位时调用 `executeTask()`。
6. 主进程执行现有审查流程，并通过 `task:progress` 发回进度事件。
7. 渲染层按任务映射更新对应任务卡。
8. 任务完成后进入历史任务，调度器启动下一条等待任务。
9. 用户点击查看报告，右侧预览绑定到该任务。

## 测试方案

### 渲染层单元测试

- 连续提交 3 个任务时，前 2 个进入运行中，第 3 个进入等待中。
- 第 1 个任务完成后，第 3 个自动开始。
- 表单提交入队后按钮恢复可点击。
- 进度事件只更新匹配任务，不更新其他本地任务。
- 成功任务仍可点击“查看报告”。
- 失败任务展示错误信息并继续调度下一条。
- 历史任务不展示 Codex 日志。

### 主进程测试

主进程现有 `executeReviewTask()` 可以保持单任务测试。并发调度放在渲染层后，主进程不需要引入全局并发状态。

需要补充或调整：

- `report:download-current` 在传入 `taskId` 时优先打开该任务报告。
- 多个任务成功后，选中任务的报告位置不会被最后完成任务覆盖。

### 集成验证

- 手动连续提交 3 条任务，确认同时最多 2 条进入 Codex 执行。
- 确认第 3 条显示等待中，并在任一运行任务结束后自动开始。
- 确认两个运行任务的日志分别显示在对应任务卡。
- 确认查看任意成功任务报告时，右侧预览和报告位置都对应同一任务。
- 确认客户端关闭后，未开始等待任务不会恢复。

## 风险与缓解

1. **本地状态复杂度增加**：通过 `useTaskQueue` 集中管理调度，避免把队列逻辑散落在组件里。
2. **进度事件串任务**：移除宽松 local 匹配，使用明确 ID 映射。
3. **报告预览被并发完成覆盖**：只在未选中任务时自动预览新完成报告。
4. **用户误以为等待任务已提交到服务端**：等待区显示本地等待状态，并说明关闭客户端后不会恢复。
5. **Codex 并发占用资源**：第一版固定并发数为 2，不提供更高并发配置。

## 验收标准

1. 用户可以连续提交超过 2 个任务。
2. 任意时刻最多 2 个任务处于实际执行状态。
3. 超出的任务显示在等待中分区。
4. 运行任务结束后，等待队列自动启动下一条任务。
5. 每个运行任务的状态、进度和 Codex 日志只更新自身任务卡。
6. 成功任务可查看报告，右侧预览与选中任务一致。
7. “查看报告位置”打开选中任务的报告位置。
8. 历史任务仍能展示成功、失败、环境异常等结果。
9. 客户端重启后，第一版不恢复未开始的等待任务。
