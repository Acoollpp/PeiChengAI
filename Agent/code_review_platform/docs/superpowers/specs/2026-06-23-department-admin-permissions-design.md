# 部门管理员权限设计

## 背景

代码审查平台当前已有正式部门模型、用户部门归属、任务部门快照、重点审查方向库和任务报告下载能力。现有权限主要分为 `admin` 和 `user`：

- `admin` 拥有平台级管理能力，可管理部门、用户、任务、重点审查方向、Skill 库和客户端版本。
- `user` 只能使用自己的任务、报告和普通功能。

部门管理功能已经完成，下一步需要增加部门管理员权限。部门管理员只管理自己绑定的单个部门，核心目标是查看本部门成员生成的代码审查报告，并维护本部门的审查方向库。现有 `admin` 权限保持超级管理员语义不变。

## 已确认需求

1. 新增部门管理员角色，首版采用 `UserRole.department_admin`。
2. 部门管理员只管理自己账号绑定的单个部门。
3. 现有 `admin` 继续作为超级管理员，权限不削弱。
4. 部门管理员不新增用户，用户仍主要通过 CCH 同步产生，用户首次登录后选择部门归属。
5. 部门管理员可以进入用户管理，但只能只读查看本部门用户。
6. 部门管理员不能新增、编辑、删除用户，不能调整角色。
7. 部门管理员可以查看自己部门成员生成的任务报告，并下载 Markdown 和 PDF。
8. 报告归属按任务创建时保存的 `ReviewTask.department_id` 判断，不按用户当前部门动态变更。
9. 部门管理员可以维护绑定自己部门的审查方向。
10. 多部门共享方向和全局方向由超级管理员维护。
11. 部门管理员可以看到并使用共享方向，但不能维护共享方向。
12. 普通用户权限保持现状。
13. 用户可见提示和错误信息使用中文。
14. CCH 同步不能静默清除人工设置的部门管理员角色。
15. 部门管理员在意见管理中首版仍按普通用户口径，只看本人反馈；本期不引入部门级反馈管理。

## 非目标

1. 不实现完整 RBAC 权限表、权限点配置或角色权限后台。
2. 不支持一个部门管理员管理多个部门。
3. 不引入方向共享申请、审批或发布流程。
4. 不允许部门管理员管理部门本身。
5. 不允许部门管理员管理 Skill 库、客户端版本或平台级配置。
6. 不改变 CCH 同步创建用户的主流程。
7. 不调整历史任务的部门快照数据。
8. 不把意见反馈扩展为部门级管理能力。

## 方案选择

### 方案 A：新增 `department_admin` 角色

在现有 `UserRole` 增加 `department_admin`，保留 `admin` 作为超级管理员。后端新增角色判断和范围过滤函数，任务、报告、统计、方向库和用户列表复用统一的权限范围。

这是本次采用的方案。它符合现有代码结构，改动集中，角色语义清晰。

### 方案 B：用户表增加 `is_department_admin`

通过布尔字段表示部门管理员身份。迁移简单，但后续权限组合会分散，角色展示、前端菜单和接口判断容易出现重复逻辑。

### 方案 C：完整 RBAC

新增角色、权限、用户角色映射和后台配置。扩展性最好，但对当前单部门管理员需求过重，首版实现和验证成本偏高。

## 角色模型

### 超级管理员

`UserRole.admin` 表示超级管理员。它保持现有能力：

- 管理全部部门。
- 管理全部用户。
- 查看、下载、删除和统计全部任务报告。
- 维护全局方向、单部门方向和多部门共享方向。
- 管理 Skill 库和客户端版本。

### 部门管理员

`UserRole.department_admin` 表示部门管理员。部门管理员必须绑定一个启用部门，才能管理该部门范围内的数据。

能力：

- 只读查看本部门用户。
- 查看本部门任务和报告。
- 下载本部门任务的 Markdown 报告和 PDF 报告。
- 查看本部门任务统计。
- 新增、编辑和停用绑定自己部门的审查方向。
- 查看和使用全局方向以及包含自己部门的共享方向。
- 作为任务创建者继续管理自己的任务上传、状态和报告流程。

限制：

- 不能新增、编辑或删除用户。
- 不能调整用户角色。
- 不能查看其他部门用户详情。
- 不能删除、更新、上传或覆盖部门成员的任务和报告。
- 不能维护全局方向。
- 不能维护多部门共享方向。
- 不能维护其他部门方向。
- 不能管理部门、Skill 库、客户端版本和平台级配置。
- 不能查看本部门所有意见反馈；意见管理仍只显示本人反馈。

### 普通用户

`UserRole.user` 保持现状：

- 查看和管理自己的任务。
- 查看和下载自己的报告。
- 使用可见的全局方向、自己部门方向和包含自己部门的共享方向。
- 不能进入管理型用户列表。

## 后端权限设计

### 权限辅助函数

建议在 `app/api/deps.py` 或相邻权限模块中形成以下函数：

- `has_platform_admin_privileges(user)`：仅 `role == UserRole.admin`。
- `has_department_admin_privileges(user)`：`role == UserRole.department_admin` 且 `department_id` 不为空。
- `has_management_privileges(user)`：超级管理员或部门管理员。
- `require_platform_admin(user)`：只允许超级管理员。
- `require_management_user(user)`：允许超级管理员和部门管理员。
- `ensure_department_admin_has_department(user)`：部门管理员没有部门时抛出 403。

为了兼容现有代码，`has_admin_privileges()` 保留为超级管理员判断，只返回 `role == admin`。需要管理入口的地方不要直接复用它，应改用新的管理权限函数。

现有调用点迁移规则：

- 部门管理、Skill 库、客户端版本、CCH 同步、后台工具接口继续使用超级管理员守卫。
- 用户列表和用户详情读取改用管理权限守卫，并在函数体内按角色过滤。
- 用户新增、编辑、删除继续使用超级管理员守卫。
- 任务读取、报告读取下载、任务统计改用任务读取范围函数。
- 任务删除、状态更新、报告上传、PDF 上传、需求附件上传改用任务写入范围函数。
- 重点审查方向管理拆分超级管理员能力和部门管理员能力，不再在所有接口上统一使用本地 `_ensure_admin()`。
- 意见反馈接口本期不迁移到部门范围，继续保持超级管理员全量、普通用户和部门管理员本人范围。

### 现有本地守卫处理

`departments.py` 中的本地 `_ensure_admin()` 保持超级管理员专属，因为部门管理员不能管理部门。

`review_focus_directions.py` 中的本地 `_ensure_admin()` 不能继续作为所有方向库管理接口的统一依赖。实现时需要拆分：

- 读取方向管理列表：允许超级管理员和部门管理员，内部按角色过滤。
- 创建方向：允许超级管理员和部门管理员，内部按角色校验部门绑定。
- 编辑、停用方向：允许超级管理员和部门管理员进入，内部按方向绑定范围校验。
- 用户输入统计、统计导出、从用户输入沉淀方向：仅超级管理员。

### Router 级别依赖处理

当前代码同时存在 router 级别依赖和函数体内联检查。实现部门管理员时必须逐个审计：

- `GET /users/` 需要从 `get_current_active_admin` 改为管理权限入口。
- `POST /users/`、`PATCH /users/{user_id}`、`DELETE /users/{user_id}` 保持超级管理员入口。
- `/admin/users` 和 `/admin/review-focus-directions` 前端路由允许管理用户进入。
- `/admin/skills`、`/admin/client-releases`、部门管理页面继续只允许超级管理员进入。

### 任务范围函数

任务、报告和统计使用同一个范围过滤函数：

- 超级管理员：无过滤，读取全量。
- 部门管理员：过滤 `ReviewTask.department_id == current_user.department_id`。
- 普通用户：过滤 `ReviewTask.user_id == current_user.id`。

部门管理员的报告归属按任务创建时的部门快照判断。用户后来换部门不会改变历史任务和报告归属。

任务写入操作使用独立的写入范围函数：

- 超级管理员：可写任意任务，保持现有能力。
- 任务创建者：可写自己的任务，包含部门管理员自己的任务。
- 部门管理员：不能因为部门范围写入成员任务。

因此实现时不能只把部门管理员的读取权限加进现有 `_get_task_for_user()`。需要拆分为 `_get_task_for_read()` 和 `_get_task_for_write()`，或等价地在写接口上使用单独校验，避免部门管理员获得成员任务写权限。

任务统计中的 `reports_by_user`：

- 超级管理员统计全量用户。
- 部门管理员统计本部门任务涉及的用户。
- 普通用户不返回按用户聚合列表，保持现状。

任务列表的 `user_name` 和 `svn_username` 搜索：

- 超级管理员在全量范围内搜索。
- 部门管理员在本部门任务范围内搜索。
- 普通用户继续只看本人任务，搜索条件不扩大可见范围。

### CCH 同步规则

部门管理员角色由超级管理员在平台内人工分配。CCH 同步必须遵守以下规则：

- 新增 CCH 用户默认仍按 CCH 源数据映射为普通用户或超级管理员。
- 已存在用户如果当前角色是 `department_admin`，CCH 源数据没有明确提供 `department_admin` 时，不得降级为 `user`。
- 永久管理员 CCH ID 和明确的 CCH 管理员来源仍可设置为 `admin`。
- CCH 同步不得清空用户已有 `department_id`。
- `is_superuser` 不作为授权依据；同步后应与最终角色保持一致，即仅 `role == admin` 时为 `true`。
- `_normalize_role()` 需要识别 `department_admin`，避免未来 CCH 源明确传入该值时被回退为 `user`。

测试必须覆盖：人工设置的部门管理员经过 CCH 同步后仍是部门管理员，并且部门归属不变。

### 部门绑定规则

超级管理员创建或编辑用户时，如果角色为 `department_admin`，必须同时指定启用部门。否则后端返回 400，提示“部门管理员必须绑定部门。”

`PATCH /api/v1/users/me/department` 保持普通用户首次绑定部门的能力。部门管理员如果处于未绑定部门的异常状态，不能通过该接口自行选择管理部门，应返回 403，提示“当前账号未绑定部门，请联系超级管理员。”

## API 设计

### 用户 API

`GET /api/v1/users/`

- 超级管理员：返回全量用户，保留现有搜索和分页。
- 部门管理员：返回 `User.department_id == current_user.department_id` 的用户，保留搜索和分页。
- 普通用户：403。
- 部门管理员未绑定部门：403，提示“当前账号未绑定部门，请联系超级管理员。”

`GET /api/v1/users/{user_id}`

- 用户本人：可读取自己。
- 超级管理员：可读取任意用户。
- 部门管理员：只能读取本部门用户。
- 目标用户不存在时返回 404；目标用户存在但不在当前用户权限范围内时返回 403。

`POST /api/v1/users/`、`PATCH /api/v1/users/{user_id}`、`DELETE /api/v1/users/{user_id}`

- 仅超级管理员可用。
- 部门管理员访问返回 403。
- 创建或更新用户时，`role == department_admin` 必须绑定启用部门。

### 任务与报告 API

以下接口统一复用任务范围函数：

- `GET /api/v1/review-tasks`
- `GET /api/v1/review-tasks/{task_id}`
- `GET /api/v1/review-tasks/{task_id}/report`
- `GET /api/v1/review-tasks/{task_id}/download`
- `GET /api/v1/review-tasks/{task_id}/pdf/download`
- `GET /api/v1/review-tasks/stats`

行为：

- 超级管理员查看全量。
- 部门管理员查看本部门任务。
- 普通用户查看本人任务。

以下写操作不因为部门管理员角色扩权，但仍允许任务创建者操作自己的任务：

- `DELETE /api/v1/review-tasks/{task_id}`
- `PATCH /api/v1/review-tasks/{task_id}/status`
- `POST /api/v1/review-tasks/{task_id}/report`
- `POST /api/v1/review-tasks/{task_id}/pdf-report`
- `POST /api/v1/review-tasks/{task_id}/requirement-file`

部门管理员访问成员任务的这些接口返回 403；部门管理员访问自己创建的任务时按任务创建者权限处理。

### 重点审查方向 API

方向库沿用现有多部门绑定能力。

`GET /api/v1/review-focus-directions`

- 超级管理员：返回全量，支持全局、指定部门、多部门方向筛选。
- 部门管理员：返回绑定自己部门的单部门方向；可选择同时展示只读的全局和共享方向，页面上不提供维护操作。
- 普通用户：不能进入管理型方向列表。

`POST /api/v1/review-focus-directions`

- 超级管理员：可创建全局、单部门、多部门共享方向。
- 部门管理员：只能创建绑定自己部门的单部门方向。请求里如果传入其他部门、多个部门或空部门，后端返回 403，避免前端误传时悄悄改变用户意图。
- 普通用户：403。

`PATCH /api/v1/review-focus-directions/{direction_id}`

- 超级管理员：可编辑全量。
- 部门管理员：只能编辑绑定自己部门且只绑定自己部门的方向；可编辑标题、内容、启用状态。
- 部门管理员不能把方向改为全局、其他部门或多部门共享。
- 共享方向只能由超级管理员维护。

`DELETE /api/v1/review-focus-directions/{direction_id}`

- 超级管理员：保持现有停用行为。
- 部门管理员：只能停用绑定自己部门且只绑定自己部门的方向。
- 部门管理员停用共享方向返回 403，提示“共享方向只能由超级管理员维护。”

普通用户方向选择接口继续返回启用的全局方向、自己部门方向和包含自己部门的共享方向。

### 意见反馈 API

部门管理员菜单中保留意见管理入口，但首版不扩展部门级反馈管理。

- 超级管理员：保持现有全量反馈列表、详情、截图、统计和状态更新能力。
- 部门管理员：与普通用户相同，只能查看、创建和统计本人反馈。
- 普通用户：保持现状，只能查看、创建和统计本人反馈。
- 首页或意见管理统计如果读取反馈统计，部门管理员按本人范围统计，不按部门范围统计。

如后续需要部门管理员查看本部门反馈，应另开规格补充反馈模型与部门快照口径。

## 前端设计

### 菜单

超级管理员菜单保持现状：

- 主页
- 部门管理
- 用户管理
- 重点审查方向
- 意见管理
- 任务管理
- Skill 库
- 客户端版本

部门管理员菜单：

- 主页
- 用户管理
- 重点审查方向
- 意见管理
- 任务管理

普通用户菜单保持现状：

- 主页
- 意见管理
- 任务管理

### 路由守卫

新增或调整前端权限工具函数：

- `hasPlatformAdminPrivileges(user)`
- `hasDepartmentAdminPrivileges(user)`
- `hasManagementPrivileges(user)`

新增路由守卫：

- `requirePlatformAdminUser()`：仅允许超级管理员。
- `requireManagementUser()`：允许超级管理员和部门管理员。

现有 `/_layout/admin` 父路由不能继续统一调用仅允许超级管理员的 `requireAdminUser()`，否则部门管理员无法进入 `/admin/users` 和 `/admin/review-focus-directions`。实现时应将权限守卫下沉到子路由：

- `/admin/users` 使用 `requireManagementUser()`。
- `/admin/review-focus-directions` 使用 `requireManagementUser()`。
- `/admin/skills` 使用 `requirePlatformAdminUser()`。
- `/admin/client-releases` 使用 `requirePlatformAdminUser()`。
- `/items` 或部门管理页面使用 `requirePlatformAdminUser()`。

重点审查方向页面保留现有路径，并允许超级管理员和部门管理员进入；后端必须做最终权限判断。

`/admin/skills`、`/admin/client-releases`、部门管理页面仍只允许超级管理员。

### 用户管理页面

超级管理员保持现有能力。

部门管理员模式：

- 列表只显示本部门用户。
- 隐藏新增用户入口。
- 隐藏编辑用户入口。
- 隐藏删除用户入口。
- 角色列显示中文角色名称。
- 可保留搜索。
- 如果当前部门管理员未绑定部门，显示中文空态提示“当前账号未绑定部门，请联系超级管理员。”

### 任务报告页面

任务管理页面复用现有 `/tasks/review`：

- 超级管理员看到全量任务。
- 部门管理员看到本部门任务。
- 普通用户看到本人任务。

部门管理员可以查看详情、读取 Markdown 报告、下载 Markdown、下载 PDF。删除、状态更新、报告上传等成员任务写操作不展示。

### 重点审查方向页面

超级管理员保持完整能力。

部门管理员模式：

- 列表展示自己部门可维护的方向。
- 可新增自己部门方向，部门字段由当前用户部门决定。
- 不显示多部门选择控件。
- 不显示全局方向创建入口。
- 不允许编辑共享方向。
- 共享方向可以在选择场景中出现，但管理页不作为可编辑项展示；如果展示，需要明确为只读。
- 用户输入统计中的跨部门筛选和导出能力只对超级管理员开放。

### 用户角色表单与类型

前端用户管理中的新增用户、编辑用户弹窗需要把角色下拉扩展为：

- 超级管理员：`admin`
- 部门管理员：`department_admin`
- 普通用户：`user`

当选择部门管理员时，部门选择为必填，并且只允许选择启用部门。

后端 OpenAPI 变更后需要重新生成前端 SDK，确保 `frontend/src/client/types.gen.ts` 等生成类型包含 `department_admin`。

Electron 共享类型需要同步更新，例如 `code_review_electron/src/shared/types.ts` 中的 `CurrentUser.role` 扩展为 `admin | department_admin | user`。

Electron 客户端部门绑定行为：

- 普通用户未绑定部门时，保持现有首次选择部门流程。
- 部门管理员已绑定部门时，不需要额外 UI。
- 部门管理员未绑定部门时，不允许在客户端自行选择管理部门，应提示“当前账号未绑定部门，请联系超级管理员。”

## 错误处理

1. 部门管理员未绑定部门访问管理范围接口：403，“当前账号未绑定部门，请联系超级管理员。”
2. 部门管理员访问其他部门用户、任务、报告、方向：403，“没有足够权限。”
3. 部门管理员维护共享方向：403，“共享方向只能由超级管理员维护。”
4. 部门管理员创建或编辑方向时传入其他部门：403，“只能维护本部门审查方向。”
5. 普通用户访问管理接口：403，“没有足够权限。”
6. 超级管理员访问保持现有行为和错误语义。

## 数据迁移

新增枚举值 `department_admin`。数据库层如果没有约束枚举类型，只需要更新应用模型和 OpenAPI 类型；如果数据库使用枚举约束，需要补充 Alembic 迁移。

历史用户不自动变更角色。部门管理员由超级管理员在用户管理页面手动设置角色并绑定部门。

实现后需要重新生成前端客户端类型，并同步 Electron 共享类型。
