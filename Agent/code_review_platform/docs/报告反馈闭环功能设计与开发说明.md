# 报告反馈闭环功能设计与开发说明

## 1. 背景与目标

本次功能围绕“AI 生成的 Markdown 审查报告是否真实有用”增加一个轻量反馈闭环。

原流程是：任务完成后，用户直接查看 Markdown 报告或打开 PDF 报告。这个流程的问题是，平台只能知道报告被生成和查看，无法知道报告中哪些内容对用户真的有帮助，也无法为后续优化 AI 报告质量提供有效数据。

调整后的目标是：

- 用户在查看报告后，需要先判断报告是否有帮助。
- 如果报告有帮助，需要标记或填写报告中真实有用的问题。
- 用户提交反馈后，系统再打开 PDF 报告位置。
- 已经提交过反馈的报告，后续再次打开时不再重复打扰用户。
- 前端先复用现有反馈接口完成闭环，后续可升级为后端结构化保存。

## 3. 用户流程设计

当前闭环流程如下：

1. 用户在任务看板中点击“查看报告”。
2. 右侧展示 Markdown 报告预览。
3. 报告工具栏先显示两个判断按钮：
   - `有帮助`
   - `没帮助`
4. 如果用户点击 `有帮助`：
   - 工具栏展示“标记有用问题”的反馈区域。
   - 报告预览中的详细标题变成可勾选项。
   - 用户可以直接勾选标题，也可以在输入框中手动补充分条问题。
   - 点击 `提交并打开PDF` 后，系统提交反馈并打开 PDF 报告位置。
   - 提交成功后，该报告在当前客户端会被标记为已提交，界面只显示 `查看PDF报告`。
5. 如果用户点击 `没帮助`：
   - 当前实现直接视为反馈流程已结束。
   - 界面切换为 `查看PDF报告`。
   - 后续可扩展为保存“没帮助”的结构化反馈。
6. 如果用户再次打开当前会话中已经提交过反馈的报告：
   - 不再显示 `有帮助`、`没帮助`、输入框和提交按钮。
   - 直接显示 `查看PDF报告`。

这个设计的核心是：用户只有完成反馈动作后，才能进入 PDF 报告位置，从而把“报告查看”和“质量反馈”串成一个业务闭环。

## 4. 交互设计说明

### 4.1 反馈入口位置

反馈入口放在报告预览页顶部工具栏，也就是原先 `查看PDF报告` 按钮所在区域。

这样设计的原因：

- 用户打开报告后，视觉焦点就在报告预览和顶部操作区。
- 不需要在 Markdown 内容内部插入复杂表单，避免遮挡报告正文。
- 反馈区域跟随报告预览页，不会因为用户滚动 Markdown 内容而被甩到页面底部。
- 提交反馈和打开 PDF 是同一个动作，用户理解成本更低。

### 4.2 “有帮助”后的反馈区域

点击 `有帮助` 后，工具栏展示一个横向紧凑反馈条，包含：

- 标题：`标记有用问题`
- 使用说明：提示用户可以勾选下方标题，或手动补充分条问题。
- 已选数量：显示当前已经记录了几条有用问题。
- 文本输入框：支持手动填写，按 `1. xxx` 的形式分条展示。
- 提交按钮：`提交并打开PDF`

该区域不放在报告正文上方或正文内部，避免遮挡阅读内容。

### 4.3 按钮样式

反馈按钮和“选择文件”等按钮使用更灵动的 hover/press 反馈：

- 鼠标悬停时轻微上浮。
- 背景和边框有轻微变化。
- 保持文字可读，不使用过亮的 hover 背景。
- 禁用状态下不做强交互提示。

按钮交互主要封装在 `TaskPage.tsx` 的 `FeedbackActionButton` 中。

## 5. 前端状态设计

核心状态位于 `TaskPage.tsx`。

### 5.1 报告反馈状态

```ts
type ReportFeedbackStatus = 'pending' | 'useful' | 'not-useful'
```

含义：

- `pending`：用户还没有判断报告是否有帮助。
- `useful`：用户点击了“有帮助”，可以选择或填写有用问题。
- `not-useful`：用户点击了“没帮助”。

### 5.2 有用问题列表

```ts
const [selectedUsefulIssues, setSelectedUsefulIssues] = useState<string[]>([])
```

该状态同时承载两类来源：

- 用户在 Markdown 预览中勾选的标题。
- 用户在反馈输入框中手动填写的问题。

为了避免出现 `1. 1. 问题` 这种重复编号，输入解析时会先去掉已有编号，再统一重新编号展示。

相关逻辑：

- `stripMarkerListPrefix`
- `parseMarkerItems`
- `formatMarkerContent`

支持去除的编号形式包括：

- `1. 问题`
- `1) 问题`
- `1、问题`

### 5.3 已提交状态

```ts
const [isReportFeedbackSubmitted, setIsReportFeedbackSubmitted] = useState(false)
const [submittedReportFeedbackTaskIds, setSubmittedReportFeedbackTaskIds] = useState<Set<string>>(
  () => new Set()
)
```

当前实现中，已提交状态保存在客户端内存里：

- 同一客户端会话内，重复打开同一个任务报告会直接显示 `查看PDF报告`。
- 应用重启后，该状态不会自动恢复。
- 换设备后也不会同步。

如果后续要做到真正的跨设备闭环，需要后端保存并返回该任务是否已经提交过报告反馈。

## 6. Markdown 标题识别设计

标题识别逻辑在 `MarkdownPreview.tsx` 中。

核心方法：

```ts
const extractDetailedHeadingOptions = (markdown: string): ReportHeadingOption[] => {
  // ...
}
```

识别规则：

1. 按行扫描 Markdown 文本。
2. 跳过代码块中的内容，避免把代码注释或示例误识别为标题。
3. 识别 `#` 到 `######` 形式的 Markdown 标题。
4. 优先选择“叶子标题”，也就是其后没有更低层级子标题的标题。
5. 优先使用三级及以下标题，即 `###`、`####`、`#####`、`######`。
6. 如果没有三级及以下标题，再回退到二级及以下标题。

这样做是为了满足“不要只选高风险问题、结论这种大标题，而要选更详细的问题标题”的需求。

示例：

```md
## 高风险问题

### 空指针风险

### 越界访问风险

## 结论
```

最终可选项会优先是：

- 空指针风险
- 越界访问风险

而不是：

- 高风险问题
- 结论

## 7. 反馈提交设计

### 7.1 当前实现方案

当前没有新增后端接口，而是复用现有通用反馈能力：

```ts
window.codeReview.submitFeedback({
  description: buildReportFeedbackDescription(...)
})
```

底层链路是：

1. Renderer 调用 `window.codeReview.submitFeedback`
2. Preload 转发到 IPC：`feedback:submit`
3. Main 进程调用 API Client
4. API Client 请求后端：`POST /api/v1/feedback`

相关文件：

- `code_review_electron/src/renderer/src/code-review-api.ts`
- `code_review_electron/src/preload/index.ts`
- `code_review_electron/src/main/ipc.ts`
- `code_review_electron/src/main/api-client.ts`

### 7.2 当前提交内容格式

当前提交给后端的是一段文本描述，格式由 `buildReportFeedbackDescription` 生成：

```text
【报告有用问题反馈】
任务ID：xxx
报告路径：xxx
PDF报告名：xxx
是否有帮助：有帮助
有用问题：
1. 问题一
2. 问题二
```

这种方式的优点是：

- 不需要立即改后端。
- 可以快速验证业务闭环。
- 和已有“提交意见”能力复用同一套链路。

缺点是：

- 后端只能保存文本，不利于做结构化统计。
- 不方便按任务、报告、问题标题维度聚合分析。
- 不能天然支持“该任务是否已经提交过反馈”的跨设备判断。

## 8. 推荐的后端结构化方案

如果后续要把该能力正式产品化，建议新增专用接口，而不是长期复用通用意见反馈。

推荐接口：

```http
POST /api/v1/review-tasks/{task_id}/report-feedback
```

推荐请求体：

```json
{
  "helpful": true,
  "useful_issues": ["空指针风险", "越界访问风险"],
  "report_path": "D:/reports/task-001/report.md",
  "pdf_report_name": "task-001.pdf"
}
```

如果用户点击“没帮助”，可以提交：

```json
{
  "helpful": false,
  "useful_issues": [],
  "report_path": "D:/reports/task-001/report.md",
  "pdf_report_name": "task-001.pdf"
}
```

后端建议保存字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 反馈记录 ID |
| `task_id` | 审查任务 ID |
| `user_id` | 提交用户 |
| `helpful` | 是否有帮助 |
| `useful_issues` | 用户选择或填写的有用问题 |
| `report_path` | Markdown 报告路径 |
| `pdf_report_name` | PDF 报告名 |
| `created_at` | 提交时间 |

任务列表或报告详情接口也建议返回：

```json
{
  "report_feedback_submitted": true
}
```

这样客户端在重启或换设备后，也能直接判断是否应该隐藏反馈 UI。

## 9. PDF 打开闭环

本次功能把 PDF 打开动作从“直接查看”改成“反馈后查看”。

当前规则：

- `pending` 状态下只显示 `有帮助` 和 `没帮助`。
- 点击 `有帮助` 后，需要至少填写或选择一条有用问题。
- `提交并打开PDF` 会先提交反馈，再调用原来的 `openPdfReport`。
- 提交成功后，按钮变为 `查看PDF报告`。
- 已提交过反馈的任务，再次打开时直接显示 `查看PDF报告`。

核心处理方法：

- `handleViewReport`
- `handleReportUseful`
- `handleReportNotUseful`
- `handleSubmitUsefulIssuesAndOpenPdf`
- `handleOpenPdfReport`

## 12. 当前限制与后续优化

当前限制：

- 已提交状态只保存在客户端内存中，应用重启后不会保留。
- 后端保存的是文本描述，不是结构化字段。
- `没帮助` 当前只在前端完成解锁，没有保存结构化的负反馈。
- Markdown 标题识别基于文本规则，复杂 Markdown 语法下仍可能需要进一步增强。

后续优化建议：

- 新增报告反馈专用后端接口。
- 后端保存 `helpful`、`useful_issues`、`task_id` 等结构化字段。
- 任务列表接口返回 `report_feedback_submitted`。
- `没帮助` 也提交负反馈，并允许用户可选填写原因。
- 将反馈条样式抽成独立组件，减少 `TaskPage.tsx` 中的内联样式。
- 对标题识别逻辑增加更多 Markdown 边界用例测试。

## 13. 总结

本次修改把“查看报告”从单纯的结果展示，升级成了一个轻量的报告质量反馈闭环。

用户在查看报告后，需要先判断报告是否有帮助；如果有帮助，则选择或填写真正有价值的问题；提交后再打开 PDF 报告。这样既不会强迫用户填写复杂表单，也能收集到比“点赞/点踩”更有价值的数据，为后续优化 AI 审查报告质量提供依据。
