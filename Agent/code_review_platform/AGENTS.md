# 项目智能体协作规则

## 通用规则

- 任何情况下都使用中文输出，包括规格、计划、Issue、PR 描述、审查结论和 Git 提交信息。
- 保留用户已有的未提交修改，不得擅自还原、覆盖或混入无关改动。
- 未经用户明确授权，不得合并 PR、直接推送到 `main`、删除分支或关闭 Issue。

## CodeGraph

当仓库根目录存在 `.codegraph/` 时，需要理解、定位或评估代码影响范围，必须先使用 CodeGraph，再使用 `rg` 或直接读取文件：

- 优先使用 MCP 的 `codegraph_explore`；不可用时使用 `codegraph explore "问题或符号"`。
- 查询文件或符号时，要求返回当前源码及调用路径，不能只依赖文本搜索推断调用关系。
- 完成代码修改和验证后，执行 `codegraph sync .`，并用 `codegraph status` 确认索引为最新状态。

如果仓库没有 `.codegraph/`，不得自行创建索引，直接使用常规代码检索工具。

## Mac 本地验收环境（固定约定）

这台 Mac 上的本地验收环境是长期固定环境，不得在每次启动时改用 Compose 新建的空数据库：

- 现网 1.x 服务固定为 `http://172.23.17.242:8000`；它不是这台 Mac 的本地验收服务。本地开发、验收或 Issue 分支不得替换、重启或修改该服务。
- 这台 Mac 的本地验收后端固定使用 `http://127.0.0.1:8001`；Electron 验收客户端应指向此地址。需要 Web 管理端时，固定在 `http://127.0.0.1:5174` 启动，并设置 `VITE_API_URL=http://127.0.0.1:8001`。
- `8001` 后端固定连接 PostgreSQL 容器 `pc-local-db-15543`，主机端口 `15543`，数据库 `review_inputs_manual_20260616`，Docker 卷 `code_review_server_test_app-db-data`。该库是从正式服务数据复制的本地副本，用于保留既有用户、API Key、部门和历史任务。
- 不得让 `8001` 连接 Compose 默认容器 `code_review_server-db-1` 或 Docker 卷 `code_review_server_app-db-data`；该库可能仅有临时验收账号，会导致原账号和 Key 登录返回 `401`。
- 启动或重建 `8001` 前，必须先检查容器的 `POSTGRES_SERVER`、`POSTGRES_PORT` 和 `POSTGRES_DB`，并在启动后对比 `review_inputs_manual_20260616` 的用户与 API Key 数量，禁止仅以健康检查通过判定环境正确。
- 当新分支引入数据库迁移时，先备份 `review_inputs_manual_20260616`，再对本地副本执行迁移；不得为了省事创建空库替代它。不得将本地验收数据回写到现网。

如果实际运行状态与上述约定不一致，先视为环境配置错误并修正，不得默认为用户账号或正式数据副本已失效。

## 旧功能保护规则

新功能不能破坏旧功能。每次改动都必须回答：

1. 这次改动影响哪些旧入口？
2. 哪些旧字段、旧接口、旧 IPC、旧文件路径需要兼容？
3. 旧客户端或历史数据不带新字段时会怎样？
4. 失败时是否会阻断原有主流程？
5. 是否需要保留原按钮文案、原下载逻辑、原状态语义或原权限范围？

默认策略：

- 新字段尽量 nullable，并为历史数据留空值兜底。
- 旧接口需要继续支持时，不删除旧字段或旧上传参数。
- 文件存储新目录要独立，避免混用报告、Skill、客户端发布包、反馈附件。
- 附件上传、PDF 上传、反馈截图等副流程失败时，除非需求明确，否则不阻断核心审查任务。
- 新 UI 入口不要改变用户已有关键工作流，除非需求明确。
- 新统计口径必须说明时间范围、权限范围和空值处理。

回归验证不能只跑新测试，至少要跑受影响模块的旧测试，并对关键链路做一次人工或端到端验证。

跨端同步清单、各端验证命令和已知陷阱以 `CLAUDE.md` 为准（§3 跨端契约、§4 各端速查、§8 陷阱清单），本文件不重复维护。

## GitHub Issues 与 PR 交付流程

所有通过 GitHub Issue 管理的开发任务必须遵循以下流程。Issue 从创建到关联 PR 合并期间始终保持打开，不得因为智能体已经完成编码或自动化测试而提前关闭。

### 1. 待智能体处理

- 创建 Issue，写清问题、范围、依赖关系和可验证的验收标准。
- Issue 保持 `OPEN`，添加 `待智能体处理` 标签；`bug`、`enhancement` 等类型标签可以同时保留。
- 每个 Issue 必须由一个新的子智能体负责实现和第一轮自测，不能复用已经实现过其他 Issue 的子智能体代替这一职责。

### 2. 开发、自测与独立二次审核

- 实现子智能体完成代码修改和与风险相匹配的自测，并报告修改文件、测试结果和残余风险。
- 实现过程中遵守「旧功能保护规则」。
- 实现完成后，必须由未参与该 Issue 实现的智能体进行独立二次审核；主智能体也可以作为独立审核者。
- 独立审核必须检查规格符合性、行为回归、测试缺口和代码质量，不能只复述实现者的自测结果。
- 审核发现问题时，Issue 继续保持 `OPEN` 和 `待智能体处理`，修复后重新进行自测与独立审核。

### 3. 推送功能分支并创建 Draft PR

- 只有实现、自测和独立二次审核全部通过后，才允许提交并推送功能分支。
- 提交信息、分支改动和 Issue 范围必须一致，不得混入无关修改。
- 推送后创建 Draft PR，并在 PR 中关联对应 Issue。需要合并后自动关闭时，在 PR 描述中使用 `Closes #<Issue编号>`。
- Draft PR 只是等待人工验收和最终审核的候选改动，不代表已经可以合并，也不得关闭关联 Issue。

### 4. 待人工验收

- Draft PR 创建成功后，从 Issue 移除 `待智能体处理`，添加 `待人工验收`，Issue 仍保持 `OPEN`。
- 向用户提供可复现的本地测试环境、测试入口、必要数据和验收步骤。
- 人工验收结果必须记录在 Issue 或 PR 中。
- 人工验收失败时，移除 `待人工验收`，重新添加 `待智能体处理`，记录失败现象并回到开发、自测和独立二次审核阶段。

### 5. Ready、最终审核与待合并

- 只有人工验收通过后，才可以把 Draft PR 标记为 Ready for review。
- Ready PR 必须完成最终代码审核和 CI 检查；存在阻断项时不得进入待合并状态。
- 最终审核和 CI 全部通过后，从 Issue 移除 `待人工验收`，添加 `待合并`，Issue 继续保持 `OPEN`。
- 进入 `待合并` 不等于授权合并；仍需用户明确确认。

### 6. 合并与关闭

- 获得用户明确授权后，才允许将 PR 合并到 `main`。
- PR 合并后，由 `Closes #<Issue编号>` 自动关闭关联 Issue，不得在合并前手动关闭。
- 合并后重新读取 PR 和 Issue 状态，确认 PR 已合并、Issue 已关闭，并移除不再适用的流程标签。

### 状态流转

```text
OPEN / 待智能体处理
  -> 子智能体开发和自测
  -> 独立智能体二次审核
  -> 推送功能分支并创建 Draft PR
OPEN / 待人工验收
  -> 人工验收通过
  -> PR Ready + 最终代码审核 + CI
OPEN / 待合并
  -> 用户明确授权合并
MERGED / Issue 自动关闭
```

任何阶段失败，都必须回到对应的处理阶段，Issue 保持打开，并在 Issue 或 PR 中留下可追溯的原因和验证结果。
