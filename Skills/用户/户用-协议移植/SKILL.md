## 默认输入

默认把用户提供的“新的协议 `.c` 文件”当作主要输入，而不是协议 PDF、Word 或 `can_code/` 草稿。

对于协议名、源文件名、英文名、中文名、枚举值这类基础信息，优先从协议 `.c` 文件头部已有的说明注释块提取和核对；当前项目里大量正式协议都遵循这一写法，因此当后续需要补协议显示名、枚举映射、总结说明或做名称核对时，应先检查该注释块，而不是跳过现成信息去猜。

若用户没有额外提供协议文档，也要优先依据：
- 当前项目现有正式代码结构
- 用户提供的新 `.c` 文件内容
- 用户提供的新 `.c` 文件头部说明注释块中的协议元信息
- 当前工程的协议枚举、协议表、全局变量、配置项和特殊逻辑

若当前工程里找不到该协议对应的正式 `.c` 文件，或找不到同族已挂接实现可以作为参考模板，就必须提醒用户提供目标枚举值；不要自行猜测要新增到哪个枚举名、枚举值或协议号。

不要把“缺少协议文档”当作停止理由。

## 核心目标

把一份外来的协议 `.c` 文件真正移植到当前项目里，而不是只做文件复制。

完成标准至少包括：
- 协议文件进入正确目录
- 协议枚举和协议切换入口补齐
- 对应头文件声明补齐
- `can_comm.h` 里的函数接口声明必须按协议 `.c` 文件里实际存在的函数逐项补齐；不要保留未实现函数的多余声明
- 协议表挂接完成
- 工程文件列表补齐
- 协议 `.c` 文件头部说明块中的协议名、源文件名、英文名、中文名、枚举值已被核对并作为优先参考来源记录
- 协议显示使用的中文名和英文名都要记录并核对来源，后续补协议表、显示名或输出总结时统一参考
- 该协议依赖的特殊参数、全局变量、从机索引、控制位、定时器、状态结构也同步补齐

如果现有代码证据不足以确认某个公共结构、全局变量或切换链路，就要明确写成“待确认”，不要为了凑完整度凭空补代码。

## 执行原则

始终按这个优先级判断：
1. 用户明确提供的新协议 `.c` 文件
2. 当前工程真实可编译的正式协议实现
3. 当前工程头文件、枚举、协议表和配置结构
4. 当前工程中同族协议的特殊逻辑
5. 历史注释和相似协议

不要把“看起来像某个品牌旧协议”当成充分证据。

同族参考必须优先选择“当前工程里已经正式挂接、且函数骨架最接近的新协议”，不要拿目录里未挂接、被注释掉、或仅文件名相似的协议当模板。

协议枚举名和值必须优先以 `references/protocol-enum-index.md` 和当前 `User/Bms_Config.h` 为准；如果用户给的协议无法映射到现有正式参考，就先向用户要枚举值，再继续移植。
若新协议 `.c` 文件头部说明块已经明确写了协议名、英文名、中文名、枚举值或源文件名，就必须先提取这些信息，并把它们作为后续核对的重要依据；只有当注释块缺失、冲突或明显过期时，才继续向其他文件求证。

## 必须先判定协议类型

先判断它属于：
- CAN 协议移植
- 485 协议移植
- 带接收应答的 CAN
- 仅轮询发送的 CAN
- 基于统一 `User485_*` 框架的 485
- 基于 `modbus_protocol/` 公共层的独立 485/Modbus 分支
- 含特殊附加逻辑的协议

若类型没判清，就不要开始机械补文件。

判定时必须同时回答两个问题：
- 它走 `InverterCANProtocol/`、`Inverter485Protocol/`，还是 `modbus_protocol/`
- 它是“普通骨架”还是“带公共状态/寄存器框架/应答交互/专属索引/公共 Modbus 控制层”的特殊骨架

只回答第一个问题不算判定完成。

若判定结果是 `modbus_protocol/` 分支，还必须额外先回答：
- 是否已经命中 `modbus_common.h` / `modbus_ctrl.h` / `Modbus_protocol_info_s` / `Modbus_comm_ctrl_s` / `MODBUS_frame_receive()` / `MODBUS_frame_handle()` 这套公共层
- 新协议是否只是在现有公共层上补一个具体协议实现，还是反过来要求当前工程新增不存在的公共结构

若第二问未确认，就不要开始移植。

## 低自由度执行要求

不要只告诉用户“要改哪些文件”，而要把每一处修改写成以下格式：
- 触发条件：在新 `.c` 文件里看到了什么函数、变量、结构或行为
- 修改动作：因此必须补哪一个正式挂接点
- 参考来源：优先抄当前工程哪个已挂接协议的写法
- 禁止事项：哪些内容不能脑补

若你没有给出这四项，就说明分析还不够具体。

## 参考模板选择规则

### CAN 模板选择

- 若只有 `Init/MainCall/ReceiveIRQ`，且没有额外公共状态，优先找同品牌、同报文组织方式的普通 CAN 协议做模板
- 若出现 `HeartValue`、`IsCommBreakFlag`、`CommBreak` 或同类断连状态，优先按 Growatt 系列检查 `CAN_Comm.h` 公共结构
- 若出现位域控制、逆变器回写控制字、附加反馈数据，优先按 Kstar 系列检查 `CAN_Comm.h` 联合体和全局数据
- 若 `MainCall` 内明显包含多阶段发送、扩展帧、pack 轮询、产品信息分包，优先按 Pylon C 或 Kstar 这类多阶段协议核对，而不是按最简单的单循环发送协议处理

### 485 模板选择

- 若文件直接使用 `User485_*` 缓冲、寄存器区、CRC 状态，默认按统一 485 框架接入，不允许另造通信主循环
- 若出现寄存器初始化、寄存器区间常量、缓存整包回填，优先找同样是寄存器型协议做模板
- 若出现从机轮询、地址切换、专属下标，优先检查是否要像 Efore 一样把公共索引放进 `Uart_User485.h/.c`
- 若同时存在 `ReceiveIQR` 和 `DataRespond` 中的请求解析/应答发送配合，优先找同品牌已挂接协议对照收发链路

### `modbus_protocol/` 模板选择

- 若文件显式包含 `modbus_common.h`、`modbus_ctrl.h`，并通过 `Modbus_protocol_info_s` + `g_485Modbus_ctrl` + `MODBUS_frame_receive()` / `MODBUS_frame_handle()` 完成收发，优先判定为 `modbus_protocol/` 分支，而不是普通 `User485_*` 分支
- 若文件内存在 `onlyRead_reg_region`、`readWrite_reg_region`、`reg_update_callback`、`reg_set_callback`、`ALL_REG_NUM` 这类寄存器映射写法，优先参考 `modbus_protocol/` 已挂接协议，不要强行改写成 `User485_Reg_Buffer` 直填风格
- 若只缺协议私有寄存器区域、回调函数或单协议头文件，可以继续按 `modbus_protocol/` 分支移植
- 若缺的是当前工程根本不存在的公共层结构，例如新的通用控制结构、公共驱动入口、额外全局 Modbus 管理器，先停止移植并反馈缺失项，不允许边猜边造一套新的公共层

## 强制分析产物

真正开始改代码前，必须先产出一份最小移植清单，至少包含：
- 新 `.c` 文件最终归档目录
- `User/Bms_Config.h` 是否新增枚举，新增到哪一组，是否只允许尾插
- 若当前工程无对应正式 `.c` 参考，是否已经向用户确认枚举值
- 头文件声明要补哪些函数，是否还要补 `extern` 公共变量或结构
- 协议表具体要挂到哪个数组，表项里的波特率、函数指针和名称从哪里取参考
- 工程文件是否要补 `EWARM/*.ewp`、`EWARM/*.ewt`
- 是否命中特殊逻辑，需要额外补公共状态、寄存器初始化、从机索引或控制联合体
- 若走 `modbus_protocol/` 分支，还要明确：
  - 是否要新增协议私有 `.h` 文件
  - 是否依赖 `modbus_common.h` / `modbus_ctrl.h` 已有结构即可落地
  - 是否仍需补 `Inverter485Protocol/Uart_User485.h/.c` 中的声明和协议表项
  - 是否需要修改 `modbus_common.c` 中现有协议分支判断；若需要，修改依据是什么

如果在这份清单里已经发现新协议依赖当前工程不存在的公共结构、公共函数或公共控制对象，就直接标记为“禁止移植，先补公共层设计确认”，不要继续进入代码改动阶段。

如果这份清单里只有文件名，没有“怎么改”的动作描述，就继续深挖，不要交付。

这份清单还必须额外包含：
- 协议 `.c` 文件头部说明块里已经给出的协议名、源文件名、英文名、中文名、枚举值，以及这些字段与工程现状是否一致
- `can_comm.h` 本次应新增的函数声明名单，以及它们在新协议 `.c` 中对应的实际定义依据
- 协议中文名、英文名、取值来源和最终准备落到哪里使用
- 当前仍存在的“不确定项 / 待用户确认项”，不能省略不写

## 特别强调

当前项目里有不少协议移植并不是“新增一个 `.c` 文件 + 改个枚举”这么简单。

遇到下列情况，必须继续深挖：
- 该协议需要在头文件里新增全局结构体或联合体
- 该协议依赖额外状态变量、心跳值、通讯中断标志、控制位
- 该协议需要新增寄存器缓冲、从机索引、地址范围、错误码
- 该协议不仅要挂 `init`，还要挂 `receive`、`respond`、`CommBreak` 或其他回调
- 该协议要改默认配置、用户配置项或协议切换逻辑
- 该协议看似是 485，但实质上依赖 `modbus_protocol/` 公共层

只要命中以上任一项，就必须去参考文档里继续查“对应模式的具体修改动作”，不能停在提醒层面。

若命中的是“当前工程缺少必要公共结构”这一类问题，则处理动作不是“继续补代码”，而是：
- 立即停止移植
- 列出缺失的结构 / 变量 / 公共接口
- 说明这些缺失项分别在哪个现有已挂接协议中可见，或当前工程完全没有对应实现
- 等用户确认是否允许先扩公共层，再继续后续协议移植

## 禁止事项

- 不要因为名字像某个品牌，就直接复制整份旧协议的公共结构
- 不要把被注释掉的协议表项当成“当前已启用模板”
- 不要只补函数声明，不核对协议表和切换链路
- 不要在 `can_comm.h` 中声明新协议 `.c` 里并不存在的函数；即使当前不会因此报错，也要按实际实现收敛
- 不要只补协议表，不核对新 `.c` 是否还依赖头文件 `extern` 资源
- 不要忽略协议 `.c` 文件头部已经写明的协议名、中文名、英文名、枚举值等元信息，转而凭印象填写
- 不要在没有代码证据时新增全局变量、默认值、协议号含义或寄存器映射
- 不要在当前工程没有正式参考 `.c` 文件时自行臆造枚举名或枚举值
- 不要漏记协议中文名和英文名，也不要在名称来源不一致时自行拍板而不提示用户
- 不要把“可能需要”写成“已经补齐”
- 不要把 `modbus_protocol/` 分支机械塞进普通 `User485_*` 框架
- 不要在 `modbus_protocol/` 公共层缺失时临时新造 `Modbus_protocol_info_s`、`Modbus_comm_ctrl_s`、`g_485Modbus_ctrl` 等核心结构后继续移植
- 不要在结构检测失败后仍继续补枚举、补协议表、补工程文件

## 输出要求

完成任务后，至少说明：
- 这是 CAN、统一 485，还是 `modbus_protocol/` 分支移植
- 除了 `.c` 文件，还改了哪些正式挂接点
- 是否发现了附加参数或特殊逻辑
- `can_comm.h` 最终保留了哪些真实存在的声明，去掉了哪些原本不该声明的接口
- 协议 `.c` 文件头部说明块提供了哪些可直接使用的元信息，哪些字段与工程现状一致，哪些字段仍需复核
- 协议中文名和英文名分别是什么，引用自哪里
- 哪些点已经补齐
- 哪些点仍需用户确认
- 如果因结构检测失败而未移植，必须单列说明：
  - 先检测到了哪些结构证据
  - 缺了哪些当前工程不存在的公共结构 / 公共接口
  - 因此为什么不能继续移植
  - 建议用户先确认哪一层公共设计

如果是分析型任务而不是直接改工程，也必须把“触发条件 -> 修改动作 -> 参考来源 -> 禁止事项”写出来，不能只列检查文件。
