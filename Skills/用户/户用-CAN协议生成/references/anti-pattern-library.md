# 反例库

> 用途：记录项目中已经识别出的不推荐写法、易误导写法和禁止外推的历史实现。
> 使用方式：在参考项目代码和生成代码前快速检查，避免把历史问题重新写回新协议。

---

## 1. 使用原则

1. 反例库不是“批评旧代码”，而是帮助生成时避免重复犯错。
2. 只要命中反例库中的模式，就不能直接当作默认规则写入新代码。
3. 若当前协议因文档要求必须采用某种特殊写法，应在生成摘要中说明“这是协议特例，不属于反例”。

---

## 2. 高优先级反例

### 2.1 `default:` 只写 `break;`，函数后面仍会发送

- 问题：若 `switch` 结束后仍执行 `Can_TransmitData(&Can_msg_Tx);`，则错误索引下可能继续发送旧帧或残留帧。
- 不推荐写法：

```c
default:
    SendMsgIndex = 0;
    break;
...
Can_TransmitData(&Can_msg_Tx);
```

- 推荐处理：默认改为 `SendMsgIndex = 0; return;`，除非能证明后续没有发送路径。

### 2.2 明明有现成字段，仍优先使用推导值

- 问题：容易引入精度偏差、单位误差或与项目现有数据源脱节。
- 典型反例：已有 `InverterData.FccAll`，却仍优先用 `DesignCapacity * PackNum`。
- 推荐处理：先查 `references/inverter-data.md`，有现成字段就优先直用。

### 2.3 `uint8_t` 字段拆成 `value >> 8`

- 问题：虽然结果通常为 `0`，但会误导阅读者以为该字段本身是 16 位。
- 不推荐写法：

```c
Can_msg_Tx.Data[0] = value;
Can_msg_Tx.Data[1] = value >> 8;
```

- 推荐处理：

```c
Can_msg_Tx.Data[0] = value;
Can_msg_Tx.Data[1] = 0;
```

### 2.4 为简单 ASCII 数字转换额外造辅助函数

- 问题：会偏离项目常见写法，增加阅读跳转。
- 典型反例：`ToAsciiTens()`、`ToAsciiUnits()`。
- 推荐处理：直接使用 `tmp` 配合 `'0' + value`。

### 2.5 给项目既有位运算额外补无必要强转

- 问题：会把项目原生风格改写成“通用 C 写法”，降低与现有协议文件的一致性。
- 典型反例：`(uint8_t)(~BIT7)`、`(uint16_t)(BIT0 | BIT1)`。
- 推荐处理：若项目现有同类代码直接写 `~BIT7`、`BIT0 | BIT1`，生成代码也保持一致，不额外补强转。

### 2.6 给普通数字字面量额外添加无符号后缀

- 问题：会生成 `1u`、`10u`、`2730u` 这类不符合项目日常手写风格的代码。
- 典型反例：`if(InverterData.PackNum > 1u)`、`(InverterData.Vsum / 10u)`。
- 推荐处理：默认使用项目已有裸字面量写法，如 `1`、`10`、`2730`；只有当协议或项目现有代码明确需要该后缀时才允许使用。

### 2.7 少量复用的简单表达式提前落临时变量

- 问题：会把本来很直观的 `Data[x] = (uint8_t)(expr)` 写法变得更绕，不符合项目偏好的紧凑风格。
- 典型反例：
  - `Iwtmp = (int16_t)InverterData.BatteryTemp - 2730;`
  - 随后仅拆 2 个字节就写回 `Data[4]`、`Data[5]`
- 推荐处理：对普通算术表达式，若复用次数不超过 4 次，优先直接内联写到 `Data[x]`；只有当同一结果被复用超过 4 次，或明显影响可读性时，才允许使用 `tmp / wtmp / lwtmp`。

### 2.8 只依赖 skill 字段参考表，不回查真实 `Inverter_Data.h`

- 问题：当 `references/inverter-data.md` 漏字段时，会把工程里明明存在的数据源误判成不存在，进而错误保留 `TODO[未实现]`。
- 典型反例：`DeltaV`、`GmaxAddr`、`GminAddr`、`TmaxAddr`、`TminAddr` 已在真实头文件中存在，但生成时仍写成“无数据源”。
- 推荐处理：`references/inverter-data.md` 只作为速查入口；只要生成代码要引用 `InverterData`，都必须回到项目真实 `Inverter_Data.h` 再核一次。若二者不一致，以真实头文件为准，并同步修正 `references/inverter-data.md`。

### 2.9 对已确认安全可做的功能帧无故省略

- 问题：会导致生成结果停在“基础骨架”层，遗漏本来可以稳定落地的协议帧。
- 典型反例：
  - 协议中已定义 `0x315~0x318` 单体电压
  - 项目已有 `PackData[0].Vol[16]` 数据源
  - 项目现有同版本实现也已经稳定发送这些帧
  - 但生成结果仍只保留基础帧，不继续实现
- 推荐处理：若某功能帧同时满足“协议已定义、数据源明确存在、项目已有稳定实现可佐证”，默认应实现；只有在依赖缺失数据源、额外状态机、客户特化逻辑或触发条件不明时，才允许暂留 `TODO[未实现]`。

## 3. 中优先级反例

### 3.1 把其他协议的地址编码方式直接套到当前协议

- 问题：ASCII 地址和数值地址是协议定义，不是通用风格。
- 错误倾向：因为某协议用 ASCII 地址，就默认当前协议也应转成 ASCII。
- 推荐处理：地址编码方式必须以当前协议文档为准。

### 3.2 把分隔符、补位字符、保留字节写法当成项目统一规则

- 问题：这些字段常常与协议定义绑定，而不只是风格。
- 错误倾向：把 `':'`、`' '`、`0` 在不同协议间随意搬用。
- 推荐处理：字符串补位、分隔符、保留字节必须按当前协议字段定义决定。

### 3.3 把单个协议的工程状态机外推为通用架构

- 问题：项目里有些协议包含客户兼容、升级、模式切换、握手阶段切换等工程逻辑，不适合当默认模板。
- 推荐处理：只抽取共性，状态机整体不外推。

## 4. 结构类反例

### 4.1 不判协议类型就直接套 `SendMsgIndex` 模板

- 问题：会把触发应答型、扩展帧命令型协议误写成普通轮询发送协议。
- 推荐处理：必须先完成协议类型判定，再选骨架。

### 4.2 未分白名单 / 灰名单 / 黑名单就直接拿项目文件当模板

- 问题：容易把历史兼容、客户定制或特殊协议结构误吸收进 skill。
- 推荐处理：先判参考级别，再决定可否整体借鉴。

### 4.3 没完成规则阅读就直接开始生成

- 问题：最容易造成漏读 skill、混用旧规则、产生幻觉。
- 推荐处理：先完整读 `SKILL.md`、`codegen-rules.md`、`coding-style.md` 及所需引用文件。

---

## 5. 维护规则

1. 每新增一个反例，必须写清楚“为什么不推荐”。
2. 若某个反例只在特定协议类型下成立，要写明边界。
3. 若旧反例后来被协议文档证明确实是正确特例，应从反例库移除或降级说明。
