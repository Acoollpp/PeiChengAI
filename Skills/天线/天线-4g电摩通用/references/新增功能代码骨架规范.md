# 新增功能代码骨架规范

## 目标

本参考文件用于指导在当前 4G 电摩工程中生成“可继续补细节”的代码骨架，而不是只生成脱离工程的伪代码。

## 适用场景

- 用户说“先生成骨架”
- 用户说“按当前风格补一套框架”
- 用户协议资料还不完整，但希望先把结构搭出来
- 用户希望新增 V109 命令或类似协议功能

## 生成前必做判断

### 1. 判断命令类型

先判断是：

- 读命令
- 写命令
- 控制命令
- 可复用统一解析入口的命令
- 必须新建专用 parse 的命令

### 2. 判断影响范围

至少检查这些文件是否会受影响：

- `bms_data_conver_v109.h`
- `bms_data_conver_v109.c`
- `bms_data_handle_v109.h`
- `bms_data_handle_v109.c`

### 3. 判断是否需要落库

不要只解析到临时变量，优先判断结果最后要写到哪个管理结构。

如果暂时不能确定，明确写：

- `TODO[待确认落点]`

## V109 读命令骨架模板

适用于新增只读类命令。

### 常规组成

1. `group_id`
2. request 声明
3. response 声明
4. 路由表项
5. request 实现
6. response 实现
7. parse 声明
8. parse 实现

### 关键要求

- `request` 尽量只负责触发统一读请求
- `response` 先取 `data_len`
- `response` 再从 `&data[IPC_DATA_HEAD_LEN]` 取业务数据
- `parse` 里做最小长度判断
- `parse` 最终应写入管理结构或保留落点 TODO

### 推荐代码模板

```c
/* bms_data_conver_v109.h */
BMS_V109_GROUP_ID_GET_XXX = 0xXXXX,
```

```c
/* bms_data_conver_v109.c */
void bms_data_get_xxx_request(void);
void bms_data_get_xxx_response(uint8_t *data, uint16_t length);

{BMS_V109_GROUP_ID_GET_XXX, NULL, bms_data_get_xxx_request, bms_data_get_xxx_response},

void bms_data_get_xxx_request(void)
{
    bms_data_get_request(BMS_V109_GROUP_ID_GET_XXX);
}

void bms_data_get_xxx_response(uint8_t *data, uint16_t length)
{
    uint8_t *p = NULL;
    uint16_t data_len = data[5] << 8 | data[6];

    if (data_len == 0)
    {
        return;
    }

    p = &data[IPC_DATA_HEAD_LEN];
    bms_xxx_parse(p, data_len);
}
```

## V109 写命令骨架模板

适用于新增参数设置类命令。

### 常规组成

1. `group_id`
2. request 声明
3. response 声明
4. 路由表项
5. request 实现
6. response 实现

### 关键要求

- `request` 调用统一写请求接口
- `response` 优先复用 `bms_data_para_set_parse(rtn, data_len)`
- 如果协议文档未说明额外返回字段，不要凭空添加复杂解析

### 推荐代码模板

```c
/* bms_data_conver_v109.h */
BMS_V109_GROUP_ID_SET_XXX = 0xXXXX,
```

```c
/* bms_data_conver_v109.c */
void bms_data_set_xxx_request(uint8_t *data, uint16_t length);
void bms_data_set_xxx_response(uint8_t *data, uint16_t length);

{BMS_V109_GROUP_ID_SET_XXX, bms_data_set_xxx_request, NULL, bms_data_set_xxx_response},

void bms_data_set_xxx_request(uint8_t *data, uint16_t length)
{
    bms_data_set_request(BMS_V109_GROUP_ID_SET_XXX, data, length);
}

void bms_data_set_xxx_response(uint8_t *data, uint16_t length)
{
    uint16_t data_len = data[5] << 8 | data[6];
    uint8_t rtn = data[4];

    bms_data_para_set_parse(rtn, data_len);
}
```

### 推荐参考样板

优先参考当前工程中同类 `set_xxx_request()/set_xxx_response()` 的配对写法。

## 生成时优先模仿的工程特征

- 大量使用 `void bms_data_get_xxx_request(void);`
- 大量使用 `void bms_data_get_xxx_response(uint8_t *data, uint16_t length);`
- 路由表以 `{group_id, write_block, request, response}` 形式挂接
- 读命令常见表项形式：`{group_id, NULL, request, response}`
- 写命令常见表项形式：`{group_id, request, NULL, response}`

## 允许保留的 TODO

当信息不足时，允许保留少量 TODO，但必须是具体 TODO：

- `TODO[待补协议细节]`
- `TODO[待确认字段长度]`
- `TODO[待确认字节序]`
- `TODO[待确认落点]`

不要写空泛的“后续完善”。

## 输出时要补的说明

生成骨架后，说明里至少要补：

1. 参考了哪个现有函数或模式
2. 当前骨架已经闭环到哪一步
3. 还缺哪些协议细节
4. 用户下一步最好补什么资料
