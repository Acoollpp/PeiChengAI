# 通用-项目资料获取

## 概述

使用浏览器 MCP 打开项目资料入口，并通过固定浏览器数据目录持久化登录态。首次由用户手动登录后，后续优先复用已有登录态，减少重复扫码。

## 工作流

### 1. 先确认环境是否具备持久化登录能力

优先检查全局或当前项目的 Codex MCP 配置里是否存在 `chrome-devtools`，并确认其启动参数包含固定的 `--userDataDir=...`。

至少检查这些位置之一：
- `C:/Users/AOC/.codex/config.toml`
- 当前项目下的 `.codex/config.toml`

若未配置固定 `userDataDir`，先补齐，再提醒用户重载 VS Code 或重启 Codex 扩展后再继续。

推荐使用用户目录下稳定且专用的路径，例如：
- `C:/Users/<用户名>/.codex/chrome-devtools-profile`

不要使用临时目录，也不要在每次调用时改动该目录。

### 2. 首次登录时只让用户手动完成一次

当目标网站需要扫码、密码、短信验证码或企业 SSO 时：
- 用浏览器 MCP 打开目标网页登录入口
- 引导用户自己扫码或输入凭据
- 不要代替用户输入敏感凭据
- 登录完成后，重新打开一次目标系统首页或登录页，确认是否能直接进入已登录页面或至少进入“帐号已登录，只差确认”的状态

如果页面属于“管理员后台”链路，而用户只是普通成员账号，要明确指出该链路不适合普通办公登录，并改走普通网页版入口。

### 3. 后续访问时优先验证是否已免登录

再次打开目标网页时，先观察结果属于哪一类：

1. 直接进入系统首页、项目页、任务页、文档页  
说明登录态已成功复用，可继续操作。

2. 进入“帐号已登录”确认页  
说明登录态仍在，只需点击“登录”“继续”“进入工作台”等确认按钮。

3. 回到完整登录页  
说明登录态失效，提示用户重新登录一次，然后继续沿用同一个 `userDataDir`。

### 4. 获取项目资料时的执行顺序

先做入口判断，再做页面操作：

1. 打开用户给出的项目网址，或打开用户指定的平台入口
2. 判断当前是否已登录
3. 如未登录，引导用户完成一次手动登录
4. 进入目标页面后，再执行“点开项目”“进入我的任务”“打开文档”“读取页面文字”“定位按钮或表格”等操作

如果用户没有给直接链接，优先从以下入口寻找：
- Teambition 组织页、项目页、我的任务页
- 钉钉文档网页
- 其他明确支持网页登录的项目平台

### 5. 明确边界

此 skill 只处理网页登录态与网页资料获取。

不要把下列情况当作本 skill 的直接目标：
- 桌面版钉钉客户端自动化
- 本地窗口级点击或桌面 UI 自动化
- 要求长期绕过网站自身登录失效策略

若站点主动清理 Cookie、要求重新验证、切换设备校验或组织策略失效，仍可能需要用户再次登录。这不属于 skill 失败，应如实说明。

## 常见操作模板

### 模板 1：首次建立免登录环境

按下面顺序执行：

1. 检查 `chrome-devtools` 是否配置固定 `userDataDir`
2. 打开目标网页登录页
3. 请用户手动扫码或登录
4. 登录完成后再次打开目标平台入口
5. 验证是否直接进入已登录页面

### 模板 2：复用已有登录态进入项目平台

按下面顺序执行：

1. 打开用户给出的项目平台链接
2. 检查是否已经进入目标系统
3. 若只出现“帐号已登录”确认页，则点击确认按钮
4. 进入目标系统后再执行页面导航或资料读取

### 模板 3：获取资料前的确认语句

可直接告诉用户：

“我先用固定浏览器登录态打开目标网页；如果登录态仍在，就直接进入项目页面；如果失效，再请你手动登录一次，后续继续复用同一份登录环境。”

## 结果判断标准

满足以下任一条件，即可认定“以后尽量免登录”的环境已建立：

1. 重新打开目标登录地址后，直接进入系统内页
2. 重新打开目标登录地址后，仅出现“帐号已登录”确认页
3. 在同一 `userDataDir` 下，多次打开目标系统仍能保持登录状态

如果只有当前会话能登录、重开后完全丢失状态，优先回查：
- 是否真的使用了固定 `--userDataDir`
- MCP 配置是否被改回无固定目录
- 是否切换成了别的浏览器配置目录

## 产出要求

完成此类任务时，回复中尽量明确说明：

1. 当前使用的是哪个网页登录入口
2. 登录态是否已复用
3. 是否还需要用户手动登录一次
4. 当前固定保存登录态的目录是什么

不要夸大为“永久免登录”。应表述为“固定复用登录态，通常无需每次重新扫码，直到网站自身让登录失效为止”。
