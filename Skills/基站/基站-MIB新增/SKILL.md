# MIB 新增

当用户要做下面这些事时，使用这个技能：

- 根据协议文档生成新的 `.mib`
- 根据 Word/PDF 里的参数补充现有 `.mib`
- 根据截图里的参数，把新对象补进已有 MIB 文件
- 按现有模板 MIB 的格式新增对象、trap 或 pack 分组
- 从协议表提取 OID、读写属性、对象名并生成 MIB 内容

## 输入形式

支持这些输入：

- 标准 `.docx`、`.doc`、`.pdf`
- 协议截图、页面截图、表格截图
- 现有 `.mib` 模板文件
- 辅助代码文件，例如定义协议版本、命令号、对象名的 `.h/.c`

如果用户给的是“现有 MIB + 一张参数截图”，优先按“补充现有 MIB”处理，而不是重生成整份 MIB。

## 主要输出

优先输出以下结果之一：

- 新生成的 `.mib` 文件
- 在现有 `.mib` 中追加后的对象定义
- 一组可直接粘贴进 `.mib` 的对象片段

必要时补充：

- 参数映射摘要
- 哪些字段是从文档直接读取的
- 哪些字段是根据现有 MIB/代码推断的
- 哪些项仍然缺信息

## 工作流程

1. 先验证输入文件或截图是否可读。
2. 如果已有模板 `.mib`，先读取模板，严格沿用其风格。
3. 提取协议参数：对象名、编号、OID、读写属性、类型、说明、是否 trap。
4. 判断是“新增普通对象”还是“新增 trap”。
5. 如果是补充现有 MIB，只修改对应对象区，不破坏原有结构。
6. 如果模板使用 `pack0..packN` 复制模式，按同样规则展开新增对象。
7. 生成或追加 `.mib` 内容后，检查编号连续性、对象格式、pack 复制是否完整。

## 客户标识判断规则

在开始生成或补充 MIB 之前，先做客户类型判断：

1. 先询问用户是否是特殊客户。
2. 如果不是特殊客户，再判断文件名中的客户标识是否需要删除。
3. 以 `PACE-BATTERY-MIB-V1.13.mib` 为例，先判断文件名里的 `PACE` 是否保留。
4. 如果用户确认需要删除 `PACE`，则不只改文件名，还要把文件正文中与模块名、头注释、对象归属相关的同名 `PACE` 标识一并删除或同步替换。
5. 不要只改文件名，不改文件内容。
6. 如果用户没有明确说明是否保留客户标识，先暂停并询问，不要自行假设。

执行时优先检查这些位置：

- 文件名
- 模块名，例如 `PACE-BATTERY-MIB DEFINITIONS ::= BEGIN`
- 头部注释中的同名标识
- 文件内其他与模块同名的客户前缀

如果删除客户标识后需要改成新的客户前缀，应保证文件名和文件内容中的同类标识保持一致。
## 文件格式校验

在读取 Word/PDF 前，先验证文件是否真的是标准格式。

- 标准 `.docx` 一般是 ZIP 容器，文件头通常是 `PK`
- 标准 `.pdf` 文件头应为 `%PDF-`
- 如果扩展名和文件头不匹配，不要假装已经成功解析正文

如果文档不可解析，但截图、旧 MIB 或代码可用，可以继续生成，但必须明确告诉用户：
这次结果是基于截图/旧 MIB/代码回推，不是完整从原始协议文档正文直接解析得到。

## 模板 MIB 风格规则

只要用户给了现有 `.mib`，就必须优先模仿它，不要发明新风格。

必要时读取参考：
`@C:/Users/AOC/.codex/skills/基站-MIB新增/references/mib-style.md`

需要保持这些内容一致：

- 模块声明风格
- `IMPORTS`
- 节点层级结构
- 完整数值 OID 注释行
- `OBJECT-TYPE` / `NOTIFICATION-TYPE` 格式
- 命名风格，例如 `basicData`、`protoVer`、`packSn`、`LimitCurrent`
- 如果模板用了 `pack0..packN` 重复对象，也必须沿用

## 参数归类规则

### 1. 普通对象

以下参数用 `OBJECT-TYPE`：

- 状态数据
- 测量数据
- 参数配置
- 控制项
- `GET` 返回的复合字符串
- `SET` 接收的复合字符串

标准字段：

- `name`
- `subid`
- `description`
- `access`
- `syntax`
- `parent node`

如果协议没有明确写类型，默认按当前项目常见风格：

- `SYNTAX OCTET STRING`
- `STATUS current`
- 状态/测量/信息类默认 `read-only`
- 配置/设置/控制类默认 `read-write`

如果缺少明确编号，不要硬猜，直接告诉用户是哪一项缺编号。

### 2. Trap 对象

以下参数用 `NOTIFICATION-TYPE`：

- 告警
- 保护
- 故障
- 恢复通知
- 异步上报告警

## 新增现有 MIB 的规则

如果用户不是要“重生成一整份 MIB”，而是要“在现有 MIB 基础上补一个新参数”，按下面规则处理：

1. 先定位当前 MIB 的对象区和编号范围。
2. 读取相邻对象的命名、注释、缩进、空行风格。
3. 新对象必须插入到正确的编号位置。
4. 如果模板是 `pack0..packN` 复制模式，新增对象必须在每个 `pack` 下都补齐。
5. 不要只补 `pack0`。

### 截图补 MIB 的专用规则

如果用户给的是截图，而不是可直接解析的 Word/PDF，按“截图补 MIB”处理：

- 从截图里提取：序号、内容名、数据类型、字节数、OID、备注、数据示例
- 优先沿用现有 MIB 邻近对象的命名风格
- 如果截图只给中文名称，生成一个简洁、贴近项目风格的英文对象名
- 如果截图显示的是同一个 OID 下的多个字段，要先判断它是“一个复合对象”，不是多个独立对象

### 共用 OID 的处理规则

如果截图/协议表中多个字段共用同一个 OID，且示例数据是类似 `1-0`、`192-168-1-10-255-255-255-0` 这种组合形式：

- 不要拆成多个独立 `OBJECT-TYPE`
- 应定义成一个复合 `OCTET STRING` 对象
- `DESCRIPTION` 里写清格式，例如 `format: function-status`
- 生成时按一个对象处理，再在协议代码里由 `String/Cut` 解析拆分

典型例子：

- DHCP 功能 + DHCP 状态，共用一个 OID
- IP + 子网掩码 + 网关 + DNS，共用一个 OID

### pack 复制规则

如果模板 MIB 把对象复制到：

- `pack0`
- `pack1`
- ...
- `packN`

新增对象时必须整组复制。不要因为截图只出现一个 OID，就只补一组。

## 命名规则

优先沿用现有项目命名风格。

如果只有中文参数名：

- 转成简洁 camelCase
- 不要做生硬拼音音译
- 尽量参考相邻对象命名

可接受风格示例：

- `basicData`
- `packVol`
- `cellVol1`
- `protoVer`
- `trapConfig`
- `StorageInterval`
- `DHCPConfig`

如果现有 MIB 大小写不完全统一，以模板多数风格为准，不要全局纠正旧命名。

## 编号规则

协议文档、截图或参数表里的编号，默认视为权威 `subid`。

校验时：

- 检查是否连续
- 检查旧 MIB 或代码是否停在更早编号
- 如果截图/协议明确有 `75`，但旧代码/旧 MIB 只到 `74`，应以协议参数为准，并明确说明这是新增补入项

不要因为旧 MIB 缺失就静默跳过新编号。

## 输出规则

最终生成或补充的 `.mib` 应满足：

- 保留原有头部和模块结构
- 保留 `DEFINITIONS ::= BEGIN`
- 保留 `IMPORTS`
- 保留节点定义
- 新增对象格式与原文件一致
- 如果有 trap，也按模板风格生成
- 文件最后保留 `END`

如果只是补一个参数，优先修改原文件，不要无意义重排整份 MIB。

## 失败处理

如果不能完整生成，也要尽量给出有效结果。

允许的部分输出方式：

- 先只生成已确认对象
- 在回复里写明缺失项，不要在 MIB 正文里乱放占位符，除非用户明确要求
- 列出无法确认的编号或字段

禁止伪造：

- 缺失编号
- trap 含义
- 不存在的语法类型
- 没有依据的版本号

## 实战建议

1. 先验证文档或截图是否可读。
2. 读现有模板 `.mib`。
3. 再看代码或头文件作辅助比对。
4. 生成结构化参数表。
5. 生成或补充 `.mib`。
6. 最后复查：
   - 是否漏编号
   - 是否有重复编号
   - 读写属性是否合理
   - pack 复制是否完整
   - 结尾是否仍有 `END`

## 回复要求

面向用户回复时，要明确区分：

- 协议文档是否真的成功解析
- 是直接从文档/截图得到，还是从旧 MIB/代码推断
- 生成或修改后的 `.mib` 路径
- 是否还有未确认参数
