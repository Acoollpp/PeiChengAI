# 通用-代码变更审查

## 概述

这个 skill 只用于 `SVN` 两个版本之间的代码变更审查。

目标不是只列出 diff，而是结合嵌入式固件常见风险点，输出一份可直接交付的审查报告，并在结束时明确告知用户报告文件路径。

## 使用边界

适用于以下场景：
- 用户要比较 `SVN` 两个版本
- 用户要查看两个 `revision` 之间的变更
- 用户要生成代码变更审查报告
- 用户给出 `SVN` 地址、项目工作副本或本地项目路径，希望审查新旧两个版本

不适用于以下场景：
- 只做 `git diff` 审查
- 只想看单个文件的临时修改
- 只想提交 `SVN commit`，不需要变更审查

## 必须先收集的信息

开始执行前，必须先向用户确认以下四项信息，缺一不可：

1. 项目路径
2. 旧版本号
3. 新版本号
4. 审查报告输出路径

如果用户没有主动提供“审查报告输出路径”，默认使用“当前项目根目录”。

可以直接使用下面这句确认语：

```text
请提供本次 SVN 代码审查所需信息：项目路径、旧版本号、新版本号；如果你没有指定报告输出路径，我会默认输出到当前项目根目录。
```

如果用户已经给了其中一部分信息，只补问缺失项，不要重复追问全部参数。

## 执行流程

严格按下面顺序执行，不要跳步：

### 1. 确认仓库与版本信息可用

- 确认项目路径是否存在
- 确认本机可用 `svn.exe` 或其他可执行的 `svn` 命令
- 确认旧版本号、新版本号是两个明确的 `revision`
- 如果用户给的是仓库 URL，也要确认是否能访问并读取日志或导出内容

如果无法访问仓库、无法执行 `svn`、或版本号不明确，要先把阻塞点说清楚，再继续后续动作。

### 2. 获取两个版本的内容与变更清单

优先获取：
- 两个版本之间的 `s![1777276670472](image/SKILL/1777276670472.png)![1777276671559](image/SKILL/1777276671559.png)![1777276677799](image/SKILL/1777276677799.png)vn diff`
- 两个版本之间的变更文件清单
- 必要时分别导出旧版本与新版本到临时目录，再做目录级比对

如果 svn diff 返回类似 E200003: Delta source ended unexpectedly 的错误，不要把原因直接归结为“本地中文路径”或“命令写法问题”。要按下面顺序快速判定：
- 先确认同一路径的 svn cat -r 旧版本 与 svn cat -r 新版本 是否都能成功
- 再确认 svn diff --summarize 或 svn log -v 是否仍可成功返回变更清单
- 如果 svn cat 成功而 svn diff 失败，优先判断为“服务端 delta 生成链路异常、对象表示链异常，或该 revision 上的 diff 计算异常”，不要继续在原命令参数上反复尝试
- 一旦进入这个分支，立即切换到“导出两个版本后本地离线比对”的兜底方案，并在最终报告或回告中说明远端 svn diff 不可用、已改用本地导出版比对

执行本地导出兜底时，临时目录优先使用纯英文、无空格、无中文路径，例如当前工作目录下的 _svn_review_tmp，避免额外引入 Windows 中文路径编码干扰，影响后续比对、工具调用或路径定位。

正式执行时，按下面两条分支处理，不要混用：

#### 分支 A：远端 svn diff 正常
- 用 svn diff --summarize 或等价方式先拿到变更清单
- 对重点代码文件直接读取远端 svn diff
- 审查时仍以代码文件为主，必要时再补看工程文件或文档影响

#### 分支 B：远端 svn diff 异常
- 先保留 svn diff --summarize 的输出，作为权威变更清单来源
- 分别导出旧版本与新版本到英文临时目录，例如 _svn_review_tmp/old_r旧版本号 与 _svn_review_tmp/new_r新版本号
- 用本地比对方式获取正文差异，例如目录比对工具或本地文件级 diff
- 审查报告中明确写明：变更清单来自远端 svn diff --summarize，正文差异来自本地导出的两个 revision 离线比对
- 如果本地离线比对得到的文件内容一致，但远端清单仍显示 M，要把它标记为“SVN 清单有修改记录，但导出内容未见实质差异”，不要直接当作代码改动下结论
- 如果用户追问为什么耗时较长，要优先解释“远端 diff 异常，已切换到双版本导出+本地比对”，不要笼统归因为网络慢或中文路径

如果仓库较大，不要一开始就把全部非代码文件纳入重点审查。先识别真实发生变化的代码文件，再聚焦审查。

### 3. 先做范围过滤，再做重点审查

优先关注这些文件：
- `.c`
- `.h`
- 协议相关配置或结构定义文件
- 初始化、默认值、状态机、通信处理相关文件

降低优先级或只做备注的文件：
- 工程文件
- 二进制文件
- 编译输出
- 自动生成文件
- 与本次行为无关的文档文件

如果工程文件变化可能影响功能，比如宏配置、编译选项、链接脚本、协议开关，也不能直接忽略，需要在报告中标注潜在影响。

### 4. 审查时必须重点关注的风险

不要把报告写成纯粹的 diff 摘抄。需要优先寻找这些问题：

1. 行为回归
2. 新增字段、变量、结构体成员后未赋值或未初始化
3. 默认值变化导致的协议切换、功能切换或门限变化
4. 接收与发送逻辑不一致
5. 帧格式、返回长度、下标、偏移量变化导致的兼容性问题
6. 条件分支、保护逻辑、延时门限、故障判定变化
7. 协议兼容性变化，例如 `CAN/485/LCD/握手` 流程不一致
8. 新增枚举、宏、配置项后，上层或下层逻辑未同步
9. 大段重构后缺少等价性证据，存在未覆盖路径

对于嵌入式固件，尤其要检查：
- 初始化链路是否完整
- 数据来源与落点是否一致
- 通信报文拼包、拆包、长度计算是否自洽
- 默认协议、默认参数、默认保护值是否被悄然改动

### 5. 输出报告

报告需要落盘为 Markdown 文档。默认文件名取“项目路径最后一级名称 + 审查报告.md”，例如：

```text
SST22-1269审查报告.md
```

如果用户指定了输出路径，就按用户路径保存。
如果用户没有指定，就默认保存到当前项目根目录，并使用上述默认文件名。

### 6. 结束时必须明确回告文档路径

执行完成后，必须明确告诉用户：
- 本次审查比较的是哪两个版本
- 审查报告已经输出到哪里
- 报告文件的完整路径是什么

不要只说“已经生成报告”，必须给出可定位的实际路径。

## 报告结构模板

建议至少包含以下部分：

```markdown
# SVN 代码变更审查报告（r旧版本 -> r新版本）

## 1. 审查范围
- 项目路径
- 对比版本
- 审查方式
- 报告输出路径

## 2. 变更概览
- 主要变更文件
- 高风险模块
- 可能受影响的协议或功能

## 3. 主要发现
- 严重问题
- 中风险问题
- 一般问题

## 4. 开放问题与假设
- 当前无法从静态代码直接确认的问题
- 需要结合实机或联调验证的问题

## 5. 测试建议
- 建议补做的回归测试
- 建议验证的协议场景

## 6. 结论
- 整体风险判断
- 是否建议直接合入/发布
```

## 输出要求

对外回复时，优先给出“发现”，不要把“总结”放在最前面。

发现部分要满足：
- 按严重程度排序
- 指向具体文件与关键位置
- 说明为什么这是风险，不要只描述改了什么
- 能明确区分“已确认问题”和“需要进一步验证的问题”

如果没有发现明确问题，也要明确写出：
- 本次未发现明确缺陷
- 当前仍然存在的测试缺口或验证盲区

## 常用执行提示

如果用户信息不完整，可以先提示：

```text
我会按 SVN 两个版本做代码变更审查。请提供项目路径、旧版本号、新版本号；如果你没有指定审查文档输出路径，我会默认输出到当前项目根目录。
```

如果用户已经给了版本号但没给输出路径，可以直接按默认值执行，并在开始前说明：

```text
你还没有指定审查文档输出路径，我将默认输出到当前项目根目录，文件名使用“项目路径最后一级名称 + 审查报告.md”，例如 SST22-1269审查报告.md。
```

## 质量要求

执行这类任务时，默认目标不是“列完改动”，而是“帮助用户提前发现回归风险”。

因此要做到：
- 先收集完整输入，再执行
- 先缩小范围，再深入审查
- 以行为风险和兼容性风险为中心
- 文档落盘后明确回告输出路径

## 审查基本要求

当用户同时提供“代码版本差异”和“软件编码检查表”时，不能只看 `diff`，必须把检查表作为审查基线一起使用。

执行时必须满足以下要求：

### 1. 先读取检查表正文，再检查是否存在内嵌图片

- 如果用户提供的是 `xlsx`、`xls` 或其他表格检查清单，先读取工作表名称、表头、规则文本、等级和备注
- 不能因为已经拿到文本就默认完成读取，必须继续确认表格中是否存在内嵌图片、截图示例、批注图或形状对象
- 如果表格内存在图片，必须把图片视为检查表正文的一部分，不能忽略

### 2. 如果表格有内嵌图片，必须提取并查看

- 需要定位图片属于哪个工作表、靠近哪些单元格、对应哪条规则
- 需要实际查看图片内容，而不是只统计图片数量
- 需要把“文字规则”和“图片示例”做行级或规则级对应，避免只理解文字、不理解示例代码

### 3. 审查时同时依据“文字规则 + 图片示例”

- 不能只按检查表文本逐条比对
- 也不能只看图片里示例代码而忽略文字描述
- 如果图片展示了典型错误写法或推荐写法，应把它纳入审查依据
- 当文字规则较抽象、而图片给出了更具体的代码模式时，优先按“文字规则约束 + 图片示例补充解释”的方式输出判断

### 4. 输出时要区分三类信息

- 代码差异中实际发生了什么变更
- 这些变更违反了检查表中的哪条规则
- 该规则在表格图片中展示了什么示例或风险模式

### 5. 如果没有发现问题，也不能只说“无问题”

- 要明确说明本次已比对哪些检查表规则
- 要说明是否已查看内嵌图片
- 要说明当前仍缺少哪些动态验证、联调验证或运行时证据

### 6. 审查报告中建议增加“检查表符合性”章节

当本次任务带有检查表时，报告中除原有“主要发现”外，建议增加：

```markdown
## X. 检查表符合性
- 规则名称
- 规则等级
- 本次涉及文件
- 是否符合
- 依据说明（文字规则 / 图片示例 / 代码证据）
```

### 7. 对嵌入式固件项目的额外要求

如果检查表中包含通信、掉电保存、看门狗、中断、休眠、拷贝长度、计算溢出、协议兼容等条目，审查时必须优先检查这些代码路径：

- 初始化链路
- 协议收发链路
- 默认值与配置切换链路
- 中断与异常处理链路
- 存储与掉电恢复链路
- 保护、门限、超时和状态机链路

### 8. 基本原则

检查表不是“附加参考材料”，而是本次审查结论的组成部分。
只完成版本差异分析、但没有完成检查表文本和图片核对，不算完成完整审查。
