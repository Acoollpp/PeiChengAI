# 动力 CAN 协议生成技能

## 1. 适用边界

本技能只面向当前动力项目这类真实结构：
- CAN 主循环入口在 `User/Main.c`
- CAN 中断入口在 `User/Bms_Interrupt_Process.c`
- CAN 管理层在 `User/Can_Manage.c/.h`
- EM 协议命令处理在 `User/Protocol/EM_Uart_Protocol.c/.h`

先读：
- `references/当前项目CAN架构.md`
- `references/生成流程与落点.md`

如需读取协议文档，优先使用用户当前工作区里的文档，不要先假设协议类别。

## 2. 核心结论

当前项目里的 CAN 不是“户用逆变器多协议枚举 + 协议表 + 多个 `Can_xxx.c`”框架。

默认判断为：
- 单 CAN 通道
- 中断收包后入队
- 主循环中统一响应
- CAN 与 EM 协议通过 `Can_Manage.c` / `EM_Uart_Protocol.c` 互转

因此默认生成目标不是新建 `Bms_Config.h` 协议枚举和 `protocol_call[]`，而是把协议文档映射到当前真实落点。

只有当用户明确要求“扩成多 CAN 协议可切换框架”时，才允许设计新的协议抽象层；否则禁止机械照搬户用项目结构。

## 3. 默认输入与默认输出

默认输入：
- Word / docx / PDF 协议文档
- 用户粘贴的报文表、ID 表、信号表
- 当前工程源码

默认输出：
- 符合当前项目架构的 CAN 协议代码
- 默认优先输出独立协议模块，即生成 `.c/.h` 并放到 `User/Protocol/` 目录
- 新增协议模块默认对外只暴露 3 个函数：初始化函数、接收函数、发送函数
- 新增协议文件默认命名为 `Xxx_Can_Protocol.c/.h`
- 若协议来源或甲方命名能明确映射到厂商简称，文件名前缀优先使用厂商简称；例如速派奇仪表协议里“博尔通”控制器统一使用 `BET` 前缀，不继续沿用 `SPQ`
- `Can_Manage.c` 中只做最小接线：包含头文件、初始化调用、接收分发、发送调度调用；禁止把协议细节重新塞回 `Can_Manage.c`
- 必须使用单独宏定义控制协议开关，默认关闭，确保不开宏时不影响现有项目行为
- 发送函数若由外部 `10ms` 时基驱动，必须明确说明传入参数或调用方式表示的是时基触发，不要把 `1` 这类魔法数字当作协议号或报文号
- 若协议当前缺少完整数据源，允许保留 `TODO[未实现]` 或发送默认值，但必须保证工程结构完整、调用链闭合、默认关闭时零影响
- 若用户没有明确要求别的形态，默认按下面这组真实挂接点落代码：
  - `User/Can_Manage.c`
  - `User/Can_Manage.h`
  - `User/Protocol/Xxx_Can_Protocol.c`
  - `User/Protocol/Xxx_Can_Protocol.h`
- 只有当用户明确要求继续沿用 `EM_Uart_Protocol.c/.h` 内嵌方式，或者明确要求新建多协议框架时，才偏离上述默认输出

## 4. 执行流程

### 第一步：先判定是不是“现有 EM-CAN 扩展”

先回答两个问题：
- 该协议是要接到当前单 CAN 通道里，还是要新建多协议切换框架
- 它主要改发送分帧、接收重组、命令处理，还是三者都改

若用户没有明确要求新框架，默认按“现有 EM-CAN 扩展”处理。

### 第二步：回查真实挂接点

必须先回查当前工程真实调用链：
- `User/Main.c` 中 `Can_MainCall()`
- `User/Bms_Interrupt_Process.c` 中 `Can_ReceiveIQR()`
- `User/Can_Manage.c` 中 `Can_DataRespond()` / `Can_EM_DataSend()` / `Can_EM_Protocol_ReceiveIQR()`
- `User/Protocol/EM_Uart_Protocol.c` 中 `EM_DataRespond_MACRO()`、命令处理分支、缓冲区大小选择逻辑

若协议要求的行为与这些入口不一致，必须先明确偏差点，再决定改法。

### 第三步：阅读协议文档并映射

对每个报文至少提取：
- 报文方向
- 标准帧 / 扩展帧
- ID 组成方式
- 周期发送 / 事件发送 / 请求应答
- DLC
- 每个字节或位段的含义
- 数据源或目标变量
- 校验、分包、序号、结束帧规则

然后把这些内容映射到当前工程落点：
- 发送相关优先映射到 `Can_EM_DataSend()` 或其下游新增逻辑
- 接收相关优先映射到 `Can_EM_Protocol_ReceiveIQR()`
- 上层命令和业务字段优先映射到 `EM_Uart_Protocol.c`

### 第四步：决定改动形态

按以下规则判断：
- 只改 CAN 发包格式：优先改 `Can_EM_DataSend()`
- 只改 CAN 收包重组：优先改 `Can_EM_Protocol_ReceiveIQR()`
- 只改上层命令返回内容：优先改 `EM_Uart_Protocol.c`
- 需要新增协议状态变量：优先放在当前最接近使用点，避免无证据地造全局变量
- 需要新增独立帮助函数：只有在复用价值明确时才拆，禁止为了“好看”过度抽象

### 第五步：生成代码

生成代码时必须遵守：
- 优先复用现有 `CanTxPdu_DataTypeDef`、`CanRxPdu_DataTypeDef`、`Can_ParseBuffer`、`Can_TxBuffer`
- 优先保持当前“中断收包入队，主循环处理”的结构
- 优先保持当前 EM 帧头、帧尾、长度、CRC 处理方式
- 协议文档没写清楚的字段必须显式写 `TODO[未实现]`
- 没有代码证据时，不要新增所谓“协议枚举”“协议数量”“协议表”

### 第六步：生成后自检

至少检查：
- 是否接在真实入口上，而不是悬空文件
- 是否区分了发送、接收、命令处理三条链路
- 是否误把户用多协议模板套进动力工程
- 是否保留了不确定项和待确认项

## 5. 低自由度输出要求

当输出“怎么改”时，必须写成下面四项：
- 触发条件：从协议文档或源码中看到了什么证据
- 修改动作：因此要改哪个真实挂接点
- 参考来源：引用当前工程哪处代码结构
- 禁止事项：这一步不能脑补什么

如果做不到这四项，说明分析还不够具体，不能直接交付。

## 6. 明确禁止

- 不要把户用 `InverterCANProtocol/CAN_Comm.*` 那套结构直接搬进当前工程
- 不要在当前项目里凭空新增 `Bms_Config.h` 的 CAN 枚举和 `TOTAL_CAN`
- 不要看到协议文档就默认新建 `Can_xxx.c`，除非你已经说明它如何被真实入口调用
- 不要在没有文档证据时猜测 CAN ID 编码、字节序、校验规则、方向位
- 不要顺手重构 `Can_Manage.c` 和 `EM_Uart_Protocol.c` 的无关逻辑

## 7. 建议的最终说明

完成代码生成或实施后，至少说明：
- 这是在“现有 EM-CAN 架构内扩展”，还是“新建多协议框架”
- 改动落在哪些真实文件
- 发送链路改了什么
- 接收链路改了什么
- 上层命令处理改了什么
- 哪些字段已按文档实现
- 哪些字段仍是 `TODO[未实现]`
